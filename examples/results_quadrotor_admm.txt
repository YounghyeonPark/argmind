QUAD-MPC ADMM ON THE ARGMIND FUNCTIONAL SIMULATOR

Problem: BENCHMARKS.md #1 -- coupled quadrotor (4 rotor thrusts, drag,
gyroscopic cross-coupling), 12 states, horizon N=20, condensed to the
control sequence: n_var=80, constraint rows=320, density(P)=1.00.
Reference: OSQP. Numbers below are computed, not modelled.

1. THE DESCRIPTOR PROGRAM
--------------------------------------------------------------------------------------------
  descriptors: setup 4, iteration 17, residual 15
  -> 32 descriptors per checked iteration, of which the convergence test is 15 (47%).
     The sequencer analysis assumed 28 descriptors per ADMM iteration; the
     hand-written v0 sequence is 32, and the residual block is nearly half of it.
  rho=0.125 (power of two -- required, see section 6), sigma=1e-06, alpha=1.6
  dependency structure (emitted vs achievable):
  setup        4 desc  emitted chain depth   4 vs true DAG depth   4 (1.00x)  policy=minimal   2 multi-producer    0 forced
  iteration   17 desc  emitted chain depth  17 vs true DAG depth  12 (1.42x)  policy=serial    9 multi-producer    4 forced
  residual    15 desc  emitted chain depth  15 vs true DAG depth   5 (3.00x)  policy=serial    3 multi-producer    6 forced
  two-iteration unrolled block hazard-checks clean: 68 descriptors

  iteration block:
      0  SCAL fp64 [m=320]->1 t_dual = rho*z
      1  AXPY fp64 [m=320]->2 wait1 t_dual -= y
      2  SCAL fp64 [m=80]->3 wait2 rhs = sigma*x
      3  AXPY fp64 [m=80]->4 wait3 rhs -= q
      4  GEMV fp64 T=A acc [m=320,k=80]->5 wait4 rhs += A'*t_dual
      5  TRSV fp64 TRIL [m=80]->6 wait5 xt = L^-1 rhs
      6  TRSV fp64 T=A TRIL [m=80]->7 wait6 xt = L^-T xt
      7  GEMV fp64 [m=320,k=80]->8 wait7 zt = A*xt
      8  SCAL fp64 [m=80]->9 wait8 x *= (1-alpha)
      9  AXPY fp64 [m=80]->10 wait9 x += alpha*xt
     10  SCAL fp64 [m=320]->11 wait10 t = alpha*zt
     11  AXPY fp64 [m=320]->12 wait11 t += (1-alpha)*z
     12  AXPY fp64 [m=320]->13 wait12 t += y/rho
     13  SCAL fp64 [m=320]->14 wait13 z = t  (stage for in-place PROJ)
     14  PROJ fp64 [m=320]->15 wait14 z = clip(z, l, u)
     15  SCAL fp64 [m=320]->16 wait15 y = rho*t
     16  AXPY fp64 [m=320]->17 wait16 y -= rho*z

6. WHAT IMPLEMENTING THE FROZEN SPEC REVEALED
--------------------------------------------------------------------------------------------
   6a. rho must be a power of two, or the solve stalls.
       The iteration multiplies by 1/rho and by rho, both carried in the
       fp32 descriptor word 7. The ADMM fixed point needs them to be
       exact reciprocals: with an active constraint, y = rho*(1/rho)*y at
       the fixed point, so if that product is not 1 the only solution is
       y = 0 and the dual variable cannot settle.
       Run on BOTH bound sets, because the interior-optimum case (active
       set 0, y* = 0) satisfies y = 0 trivially and therefore hides it:
                   bounds     rho   recip err  CM iters  final primal res
          nominal (act 0)     0.1    1.49e-08        11         6.384e-16
          nominal (act 0)     0.2    1.49e-08        23         6.939e-16
          nominal (act 0)   0.125    0.00e+00        14         3.192e-16
          nominal (act 0)    0.25    0.00e+00        29         7.355e-16
           tight (act 10)     0.1    1.49e-08      1500         4.402e-09  STALLED
           tight (act 10)     0.2    1.49e-08      1500         2.201e-09  STALLED
           tight (act 10)   0.125    0.00e+00        34         1.260e-09
           tight (act 10)    0.25    0.00e+00        36         7.673e-10
       The runtime refuses a non-power-of-two rho by default rather than
       returning a quietly-unconverged answer; the rows above use the
       explicit opt-out.

   6b. The convergence test cannot be expressed in frozen v0.
       OSQP's criterion is stated in infinity norms. v0's only reduction
       is DOT, i.e. a 2-norm. Cost of using the 2-norm instead:
         norm  opcode  frozen v0  CM iters   |u0-u0*|inf
         LINF    NRMI         NO         9     4.224e-06
           L2     DOT        yes         8     1.545e-05
       Both programs are the same fifteen residual descriptors with one
       opcode substituted. The 2-norm test is a valid stopping rule, but it
       is not the reference solver's rule, so iteration counts published
       against OSQP would not be comparable. One opcode (NRMI) fixes it:
       no new fields, no new base addresses.

   6c. MACIF refusals fire as specified.
       cm100 + fp16: refused -- macro 'cm100' does not declare fp16 (declared: int8, bf16, fp32, fp64) refusing to build admm.setup[0] GEMM (K = rho*A'A)
       cim-inference-macro + fp64: refused -- macro 'cim-inference-macro' does not declare fp64 (declared: int8, bf16) refusing to build admm.setup[0] GEMM (K = rho*A'A)
       cim-inference-macro + fp32: refused -- macro 'cim-inference-macro' does not declare fp32 (declared: int8, bf16) refusing to build admm.setup[0] GEMM (K = rho*A'A).

   6d. Descriptor v0 limitations found by implementing it:
       [L1] No max-absolute (infinity-norm) reduction opcode.
            severity: blocking for in-fabric convergence test
            fix: One opcode (NRMI). No new fields, no new base addresses.
       [L2] Only three base addresses, so out-of-place box projection (input, lower, upper, output) cannot be expressed.
            severity: restricts kernels to in-place form
            fix: Either accept in-place-only projection as the contract (it agrees with the in-place kernel requirement) or add a fourth AGU/base address. The emit-cost analysis already flagged a fourth AGU as the open question.
       [L3] Exactly one wait token per descriptor.
            severity: removes achievable overlap
            fix: Either a second wait token (8 bits are not available in w0 -- it is exactly full) or a wait *mask* semantics change, or an explicit statement that codegen owns serialisation.
       [L4] One precision field, so operand and result formats are necessarily the same.
            severity: blocks the recommended numerics
            fix: Architect ruling: widen w0's precision field by taking bits from elsewhere, add a second header word, or declare that the accumulator format is implied by the MACIF contract for the operand format (which is nearly true already, and would be the cheap answer, but it fixes the *store* format too).
       [L5] w7 is an fp32 bit pattern, so a kernel cannot receive an exact fp64 scalar -- and it cannot receive a matched pair of reciprocal scalars unless they happen to be exact in fp32.
            severity: SILENT WRONG ANSWER unless codegen constrains rho
            fix: Cheapest: put 'rho must be a power of two' in the codegen contract and have the runtime refuse otherwise -- which it now does. Alternatives: a reciprocal-capable scalar field, or a kernel that divides rather than multiplying by a stored reciprocal.
       [L6] 16-bit dimension and leading-dimension fields.
            severity: bounded, but reachable
            fix: Codegen must tile flat elementwise ops. Cheap, but it must be in the codegen contract or it will be discovered by a customer.
       [L7] No elementwise vector multiply, and only a scalar rho field.
            severity: affects problems with equality constraints
            fix: One opcode (VMUL), three addresses, no new fields.
