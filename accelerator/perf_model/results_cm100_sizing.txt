Q2 — WHAT SIZES THE MAC ARRAY NOW? (latency: nothing. energy: solver GEMM.)
============================================================================================================
The premise of this re-run was that with ARM-MPC at 24x margin the array
becomes purely an ML feature. That is TRUE FOR LATENCY and FALSE FOR ENERGY.

Tile dimension is the operand-REUSE depth: a Tm x Tn array fetches
(1/Tm + 1/Tn) operand elements per GEMM MAC. So a bigger array does not
make the GEMM-bearing SOLVER rows faster than their deadline needs, but it
does make them cheaper. Energy per call, 64 B/cycle, 128 KB, 16 lanes:

  tile   MACs  mac mm2  core mm2  QUAD-MPC   ARM-MPC   PWR-MPC    EKF-24    EKF-96   sum uJ  d(uJ)/d(mm2)
     4     16    0.015     0.602     12.30     36.00      0.08      0.57     26.07    75.02 
     6     36    0.034     0.624     11.10     31.66      0.07      0.37     16.95    60.14           691
     8     64    0.060     0.654     11.10     29.49      0.07      0.29     13.06    54.01           203
    12    144    0.135     0.740     11.10     27.32      0.07      0.22      9.63    48.34            66
    16    256    0.240     0.860     11.10     26.24      0.07      0.19      8.09    45.68            22

  Per-row sensitivity, 64 MACs vs 256 MACs:
    QUAD-MPC          11.10 ->      11.10 uJ  (1.00x)  pure GEMV or DRAM-bound: array is dead area
    ARM-MPC           29.49 ->      26.24 uJ  (1.12x)  GEMM-bearing: array pays
    PWR-MPC            0.07 ->       0.07 uJ  (1.00x)  pure GEMV or DRAM-bound: array is dead area
    EKF-24             0.29 ->       0.19 uJ  (1.57x)  GEMM-bearing: array pays
    EKF-96            13.06 ->       8.09 uJ  (1.62x)  GEMM-bearing: array pays
    SLM-DECODE     19032.31 ->   19032.31 uJ  (1.00x)  pure GEMV or DRAM-bound: array is dead area
    VIT-TINY        1112.33 ->     646.43 uJ  (1.72x)  GEMM-bearing: array pays

  So the array is justified by: VIT-TINY on LATENCY (needs 36 MACs at 30
  fps), and EKF-24/EKF-96/ARM-MPC on ENERGY (1.3-1.6x for 64->256 MACs).
  EKF is a beachhead workload, not an ML one, so 'the array is an ML
  feature that solver customers subsidise' is NOT the right story. The
  right story is: the array is an ENERGY feature for matrix-MATRIX solver
  work (covariance recursion, Riccati factorisation) and a THROUGHPUT
  feature for ML. Marginal return collapses past 144 MACs: 84 uJ/mm2 for
  8->12, 27 for 12->16, 8 for 16->24.

  ADVERSARIAL — the cheapest way to buy this reuse is probably NOT MACs.
  The energy win above is entirely 1/Tm + 1/Tn, i.e. reuse depth. Growing
  the array buys reuse at O(T^2) area for O(1/T) traffic. An L0 operand
  register file / accumulator blocking tier below the array buys the same
  traffic reduction at O(T) area. The model cannot yet evaluate that (one
  pJ/byte for all reads, no L0 tier), and it is the single highest-value
  model extension outstanding. If an L0 tier lands, the honest array size
  drops back toward the ML-only 36-64 MACs.

  Square is optimal, so this is a one-dimensional choice: at fixed MAC
  count, (1/Tm + 1/Tn) is minimised at Tm == Tn (AM-HM). Checked:
    12x12 = 144 MACs  0.6667 operand B/MAC  EKF-96 9.63 uJ
    16x9  = 144 MACs  0.6944 operand B/MAC  EKF-96 9.82 uJ
    18x8  = 144 MACs  0.7222 operand B/MAC  EKF-96 10.06 uJ
    24x6  = 144 MACs  0.8333 operand B/MAC  EKF-96 10.78 uJ
    36x4  = 144 MACs  1.1111 operand B/MAC  EKF-96 12.89 uJ

  SOLVER-ONLY SKU — is it a real product? Yes, and it is a big saving:
  SKU                                 MACs  core mm2  solver uJ       perf/W misses (worst-case)   
  CM-100S  solver-only, min array       16     0.511      69.83   7.7-17.5   SLM-DECODE, VIT-TINY  
  CM-100S  solver-only, 64 MAC          64     0.563      50.77  11.0-20.7   SLM-DECODE            
  CM-100   proposed                    144     0.698      41.19  13.7-23.5   SLM-DECODE            
  CM-100   previous recommendation     256     0.953      42.08  11.4-23.9   SLM-DECODE            

  A 16-MAC solver-only part clears every solver deadline at worst-case
  iterations and costs 0.378 mm2 -- 54% less silicon than the previous
  recommendation. It pays 2.3x the solver energy of the 256-MAC part on
  the EKF rows, so it is the right SKU for an MPC-only socket and the
  wrong one for a state-estimation socket. Both share the MACIF boundary,
  so this is a synthesis parameter, not a second design.

Q3 — DOES THE ENERGY ARGUMENT FOR 128 B/CYCLE SURVIVE? (yes at -12%, but
     ~80% of it is a bank-geometry bet, not a bandwidth effect)
============================================================================================================
Previous claim: -15% solver energy for +0.042 mm2. Re-derived at 128 KB
with the corrected benchmarks, decomposed into its two mechanisms:

Reference point is the 64 B/cycle FLOOR, at the recommended 144 MACs /
128 KB. 'from pJ/B' is the part of the delta explained by the bank
geometry alone; 'from static' is the part explained by a shorter active
window. They should add to roughly the total delta.

 B/cyc  banks  word   pJ/B  spad mm2  solver uJ   vs 64B  from pJ/B  from static
    32      4    8B  1.319     0.234      57.72    19.4%     -6.79u       -2.60u
    64      8    8B  1.033     0.239      48.34    (ref)     +0.00u       +0.00u
   128     16    8B  0.839     0.279      43.15   -10.7%     +4.58u       +0.61u
   256     16   16B  0.747     0.294      40.66   -15.9%     +6.77u       +0.91u

  64 -> 128 B/cycle at 128 KB / 144 MACs: solver energy 48.34 -> 43.15 uJ = -10.7%,
  for +0.040 mm2 of scratchpad (+0.046 mm2 with top margin). The argument SURVIVES, at
  -11% rather than the -15% previously claimed.

  NOW THE ASSUMPTION IT RESTS ON. Of that 5.19 uJ, 4.58 uJ is pJ/byte falling
  1.033 -> 0.839 and only 0.61 uJ is the shorter active window -- so
  88% of the energy case for width is a BANK-GEOMETRY effect (16 banks of
  8 KB are cheaper per access than 8 banks of 16 KB), NOT a bandwidth
  effect: the byte COUNT a workload fetches is identical at both widths.
  That is the same [A2]-interpolation mechanism flagged in ADVERSARIAL
  CHECK 3. If the real foundry macro does aggressive column gating, pJ/byte
  goes flat with width and this -12% collapses toward -2%. The Phase-1
  compiler datasheet settles it; until then 128 B/cycle is a BET and
  64 B/cycle is the floor that does not depend on winning it.

  ARM-MPC IS fp64 -- 8 B/element. What that changes:
     64 B/cyc,  4 fp64 FMAs: fp64 GEMV ceiling   4.0 MAC/cyc -> FMA-CLUSTER-limited
     64 B/cyc,  8 fp64 FMAs: fp64 GEMV ceiling   8.0 MAC/cyc -> BANDWIDTH-limited
     64 B/cyc, 16 fp64 FMAs: fp64 GEMV ceiling   8.0 MAC/cyc -> BANDWIDTH-limited
    128 B/cyc,  4 fp64 FMAs: fp64 GEMV ceiling   4.0 MAC/cyc -> FMA-CLUSTER-limited
    128 B/cyc,  8 fp64 FMAs: fp64 GEMV ceiling   8.0 MAC/cyc -> FMA-CLUSTER-limited
    128 B/cyc, 16 fp64 FMAs: fp64 GEMV ceiling  16.0 MAC/cyc -> BANDWIDTH-limited

  fp64 halves the MAC/cycle a given B/cycle can feed, but ARM-MPC's
  4000 us deadline is 16x QUAD-MPC's 1000 us while its op count is only
  ~2x, so external/scratchpad bandwidth does not bind it. RESOLVED
  2026-07-30: the fp64 DATAPATH is now costed explicitly -- see
  perf_model/fp64_datapath.py. The 0.125 rate factor on the bf16 array is
  gone; fp64 throughput is now an absolute FMA count that carries area.
  Summary of that analysis: 8 merged multi-format FMAs, +0.072 mm2 over an
  honest fp32-only vector unit, ARRAY-bound not bandwidth-bound on fp64.

Q4 — CAPACITY: 128 KB does NOT suffice. OVERTURNED 2026-07-30 by MEASUREMENT
============================================================================================================
This section previously concluded 'yes, and it is better on every axis'.
The functional simulator's MEASURED static allocation plan for QUAD-MPC
contradicts it: 163.8 KiB at fp32 against the 128 KB that was costed. The
measurement is authoritative over the model. Two errors, both flattering:

  (1) P and L were charged n^2/2 each -- a PACKED triangular layout. Packed
      triangular addressing puts row i at element offset i(i+1)/2, which
      base+leading-dimension AGUs CANNOT EXPRESS. The capacity model was
      assuming a storage layout the descriptor format cannot address.
      Undercount: 25600 B.
  (2) Working vectors and residual temporaries were charged ZERO. They are
      14136 B at fp32 -- 10% of a 128 KiB scratchpad -- structurally
      invisible because the field is named `persistent_bytes` and a
      temporary is not persistent.

  Exact decomposition: 102400 (model) + 25600 (identity block materialised)
  + 12800 (P) + 12800 (L) + 14136 (vectors) = 167736 B measured. No
  residual term, which is what makes it a diagnosis rather than an estimate.

  WHY 128 KB WAS ARITHMETICALLY IMPOSSIBLE, not merely tight: the flagship's
  three matrices ALONE are Gamma 76800 + P 25600 + L 25600 = 125.0 KiB of a
  128.0 KiB scratchpad, leaving under 3 KiB for every vector in the program.
  Even aliasing every temporary that legally can (rp onto Ax, rd onto Px,
  zt onto Ax, t onto t_dual, xt onto rhs, sigma deleted by a zero-stride
  broadcast) lands at 134.1 KiB. The conclusion does not rest on the
  implementation's profligate vector allocation.

  fp64 IS NOT THE TARGET. 327.6 KiB at fp64 is a VALIDATION artefact: the
  implementation runs fp64 to match OSQP bit-for-bit. ADMM's measured
  control-action error at fp32 is 4e-7, and fp64 is an interior-point
  requirement (ARM-MPC), not an ADMM one. Do not size against it.

Corrected persistent footprints (P and L as dense squares because that is
what the AGU addresses, A = [I;Gamma] so the identity block stores nothing,
working vectors counted; ARM-MPC is fp64 so 8 B/element):

  The determinism claim is 'no DRAM in the control loop'. It is only

  RULING: 192 KB, 16 banks x 12 KiB. Bandwidth (128 B/cycle) and bank
  count (16) DO NOT MOVE -- this is a capacity correction, not a
  rebalancing, and it does not touch the bandwidth-first finding.

  Cost, and it is a real cost: scratchpad 0.203 -> 0.279 mm2 (+0.077),
  core 0.698 -> 0.786 mm2 (+12.6%), pJ/byte 0.718 -> 0.839, leakage 0.52
  -> 0.78 mW at 85C, solver energy +5.5%, QUAD-MPC perf/W 14.13x ->
  12.55x. Latency does NOT move (36.0 us either way): capacity was never
  the binding constraint and still is not.

  WHY 192 AND NOT 160: 160 KB fits the 138.8 KiB basis at 86.8% and would
  be the cheaper answer if bank geometry were linear. It is not. 10 KiB
  per bank is a 1280x64b macro with array efficiency 0.354, against 0.394
  for 12 KiB (1536x64b), so the last 32 KiB costs only 0.020 mm2 and 160 KB
  is DOMINATED on area per bit. 192 KB also holds the NAIVE 163.8 KiB
  layout at 85.3%, so the flagship fits even from a code generator that
  has not done the A = [I;Gamma] optimisation -- that robustness is most
  of the argument.

  REJECTED, with reasons, so none of these returns as a new idea:
   * packed-triangular AGU mode: saves 12.8 KiB -> 125.7 KiB = 95.9% full.
     A 4% margin on a +/-2x modelled footprint is not a margin. Keep it as
     a later optimisation, not as a sizing mechanism.
   * overlay P and L in one square: saves 25.6 KiB but needs THREE new
     hardware behaviours (triangle-masked GEMM output, symmetric-from-
     strict-upper GEMV, transposed triangular elementwise add) plus a
     separate diagonal buffer, because P's diagonal and L's collide.
     Control logic costs more than 0.026 mm2 of SRAM.
   * eliminate P algebraically (P*xt = sigma(x-xt) - q + A'(rho*z - y -
     rho*zt)): reaches 113.8 KiB but costs an extra Gamma' GEMV per check
     (+44% on the residual block) and returns a residual that is NOT
     OSQP's. Refused for the same reason the 2-norm termination substitute
     is refused; accepting one and rejecting the other would be incoherent.
   * require fp16 operands: reaches 101.3 KiB, but fp16 is an OPT-IN
     codegen mode, so it cannot be the default sizing basis.
   * stream the overflow: only 0.026 GB/s at 1 kHz, so the BANDWIDTH is
     trivial -- but it puts DRAM in the flagship control loop and forfeits
     the determinism claim on the one row where determinism is the
     product. Retained only as an explicit small-SKU option.
   * 64 KB: rejected outright; QUAD-MPC would stream every 1 ms tick.

  static estimate is a LARGER fraction of the total. EKF-24 still falls
  below the 5x kill criterion ungated. Coarse-grain power gating plus a
  retention-mode scratchpad remains a REQUIREMENT. Measure static power in
  Phase 1: it is now the most load-bearing single [EST] in the model.

============================================================================================================
ADVERSARIAL CHECK 3 — why pJ/byte falls with width, and where it breaks
============================================================================================================
   128 KB   8 banks x  8 B ( 64 B/cyc): macro 0.654 + wire 0.170 + mux 0.060 = 0.884 pJ/B
   128 KB  16 banks x  8 B (128 B/cyc): macro 0.478 + wire 0.179 + mux 0.060 = 0.718 pJ/B
   128 KB  16 banks x 16 B (256 B/cyc): macro 0.406 + wire 0.185 + mux 0.060 = 0.652 pJ/B
   256 KB   8 banks x  8 B ( 64 B/cyc): macro 0.873 + wire 0.210 + mux 0.060 = 1.143 pJ/B
   256 KB  16 banks x  8 B (128 B/cyc): macro 0.654 + wire 0.216 + mux 0.060 = 0.930 pJ/B
   256 KB  16 banks x 16 B (256 B/cyc): macro 0.535 + wire 0.221 + mux 0.060 = 0.816 pJ/B

  Two independent mechanisms are conflated in 'wider is cheaper': (a) a
  read activates a whole wordline, so sensing more of it is cheaper per
  byte [A2, 45nm, measured]; (b) more banks means SMALLER banks, and small
  macros are cheaper per access. Both are directionally real. Both are
  interpolations of one 45nm dataset scaled by a single 0.30 factor. The
  -12% energy case for 128 B/cycle and the -10% case for 128 KB are the
  SAME BET made twice, so they are correlated, not additive evidence. If
  the bet loses, the CM-100 should be 64 B/cycle at 128 KB and the
  128 KB decision survives anyway (it is also -0.134 mm2 and half the
  leakage, neither of which depends on the energy model).

  DECISIONS AND WHAT THEY REST ON
   * 128 KB, 128 B/cycle, 144 MACs is the ENERGY-KNEE point. Every part of
     it is a synthesis parameter, so none of it is irreversible.
   * 64 B/cycle / 64 MACs / 128 KB (0.654 mm2) is the FEASIBILITY FLOOR:
     it meets every deadline in the set at worst-case iteration counts
     inside a 50%-of-period budget. If the Phase-1 macro datasheet shows
     flat pJ/byte vs access width, DROP TO THE FLOOR -- the entire case
     for the wider, larger part evaporates with it.
   * Sensitive to, in order: (1) foundry macro pJ/byte vs access width and
     vs macro size -- one 45nm dataset, one scale factor, two correlated
     -10% claims; (2) static power (15 mW [EST]) which sets ungated
     perf/W; (3) the fp64 FMA gate count (26.6-56.2 kgates, a 2.1x band
     that moves core area 0.79 -> 0.93 mm2); (4) PERIOD_BUDGET=0.50,
     which is what makes 64 B/cycle rather than 32 B/cycle the floor.
     At 100% of period, 32 B/cycle suffices.
   * MEASUREMENTS THAT WOULD FIRM THIS UP: foundry SRAM compiler energy
     tables at 8/16/32 B access width and 8/16/32 KB macro size; measured
     cold-solve iteration tails for PWR-MPC and ARM-MPC (both [EST]);
     synthesis area + energy for one merged fp64/2xfp32 FMA at 800 MHz
     (CVFPU/FPnew is open source -- this is a one-day Yosys/OpenROAD run
     and it closes the largest remaining area uncertainty).

  WHAT DID NOT CHANGE: bandwidth-first over MAC-first (the ADMM rows are
  still GEMV-bound and still bind on scratchpad bandwidth, just at a lower
  absolute width); the >=5x kill criterion (passes 12-22x); zero-copy and
  residency; power gating as a requirement. SLM-DECODE still misses by
  3.4x and is still an external-bandwidth provisioning problem.
