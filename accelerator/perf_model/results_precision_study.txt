==============================================================================================
PRECISION FLOOR STUDY — numerical demonstration (MEASURED numerics, not silicon)
==============================================================================================
Tests three prose claims that carry real area. Each is written so it CAN fail.

C1 — EKF covariance recursion: is fp32 the floor, in every filter form?
          form   prec   survived   min eigenvalue   verdict
------------------------------------------------------------------------
  conventional   fp64      60/60        3.612e-03   STABLE
  conventional   fp32      60/60        3.752e-03   STABLE
  conventional   bf16       0/60       -1.791e+03   LOST POS-DEF
  conventional   fp16       0/60              inf   LOST POS-DEF
        joseph   fp64      60/60        3.181e-03   STABLE
        joseph   fp32      60/60        3.571e-03   STABLE
        joseph   bf16       0/60       -1.983e+03   LOST POS-DEF
        joseph   fp16       0/60              inf   LOST POS-DEF
          sqrt   fp64      60/60        3.238e-03   STABLE
          sqrt   fp32      60/60        3.885e-03   STABLE
          sqrt   bf16       0/60              inf   LOST POS-DEF
          sqrt   fp16       0/60              inf   LOST POS-DEF

  Reading: a filter that loses positive-definiteness has diverged — the
  covariance no longer represents an uncertainty. This is the failure mode
  square-root filters exist to avoid.

   1e-02    3.10e+02    6.78e-15    6.13e-07    5.68e-13   yes
   1e-04    2.12e+05    2.01e-14    2.08e-06    8.22e-12   marginal
   1e-06    1.56e+07    6.76e-15    2.13e-06    7.96e-12   marginal
   1e-08    1.88e+09    5.23e-15    3.26e-06    1.51e-11   marginal

   1e-12    1.98e+13    7.06e-15    5.12e-06    2.84e-11   marginal

  'fp32+1 IR' = one step of iterative refinement with the residual computed

C4 — FCS-MPC: does a narrow operand format change the SELECTED switching
     sequence? (three-level NPC, |U|=27, Np=2 -> 729 sequences, 200 trials)
  operand prec  argmin disagrees   mean cost penalty     worst
----------------------------------------------------------------
          fp64             0.0%            0.00e+00  0.00e+00
          fp32             0.0%            0.00e+00  0.00e+00
          fp16             3.0%            1.47e-06  1.02e-04
          bf16            11.0%            9.16e-05  4.21e-03

  'cost penalty' = excess TRUE cost of the chosen sequence as a fraction of
  the full cost spread across candidates. Disagreement alone is NOT a defect:
  when two candidates are within epsilon, either is within epsilon of optimal.
  The number that would kill a format is a large PENALTY, not a large
  disagreement rate. Note the plant is deliberately near-unity-eigenvalue,
  which packs the candidate costs close together — a well-separated plant
  would flatter every format.

==============================================================================================
VERDICTS
==============================================================================================
C1  CONFIRMED, strongly. fp32 is stable over 60 steps in all three filter
    forms; bf16 and fp16 lose positive-definiteness on the FIRST step in all
    three, square-root form included. fp16 overflows outright at kappa(P)=1e6,
    so for the EKF the binding limit is dynamic RANGE as well as precision.
    -> The 'fp32 minimum, no 16-bit path in any filter form' requirement holds.

C2  INCONCLUSIVE — and the fp64 requirement is NOT measured by this study.
    The mechanism is confirmed: kappa(K) grows 3.1e2 -> 2.0e13 as mu falls
    1e-2 -> 1e-12, exactly the ~1/mu behaviour claimed. But the accuracy loss
    does not follow: fp32 forward error stays ~5e-6 even at kappa=2e13, about
    1e7 times better than the kappa*epsilon bound, because a synthetic KKT
    matrix with a huge well-separated -diag(s/z) block is benign for LU with
    partial pivoting. Real interior-point ill-conditioning comes from a MIX of
    active and inactive constraints in one matrix plus a nearly-singular
    reduced Hessian, which this construction does not reproduce.
    -> fp64 for interior-point currently rests on the literature and the
       solver-numerics audit, NOT on this experiment. Do not cite this as
       measured support. Settling it needs a real IP iteration sequence.

C3  PARTIALLY CONFIRMED, with one claim too strong and one bonus finding.
    The directional claim HOLDS: the cached triangular solve is ~3x more
    sensitive than the operands (6.1e-2 vs 1.9e-2 control-action error), so
    'the solve must not be low precision' stands.
    But 'ADMM tolerates bf16 operands' is TOO STRONG: bf16 operands cost 1.9e-2
    -- ~2% error in the commanded control action -- while fp32 operands cost
    4.0e-7. 2% is not obviously acceptable for a constrained system and should
    not be assumed away.
    BONUS, and actionable: fp16 operands (1.9e-3) beat bf16 (1.9e-2) by 10x,
    because for these matrices MANTISSA BITS matter more than exponent range
    -- the opposite of the ML tradeoff that makes bf16 the default. If 16-bit
    operands are ever used to double effective GEMV bandwidth on the ADMM rows
    (which are bandwidth-bound, so this is worth ~2x latency), the format
    should be fp16, not bf16. The MAC array is currently specified bf16.

==============================================================================================
LIMITS OF THIS STUDY
==============================================================================================
  * THREE of the experiments here were invalid on first write, all in the same
    family -- comparing across precisions without holding the problem fixed,
    or measuring a quantity that is not comparable across variants. The first
    C3 version even showed bf16 'beating' fp64. Each is documented in the
    relevant docstring. Treat any cross-precision comparison with suspicion
    until its reference row scores exactly zero, as C3's now does.
  * Emulates STORAGE precision with fp32/fp64 arithmetic. Real hardware also
    rounds intermediate products; a true bf16-multiplier datapath may be
    slightly worse than shown here.
  * Uses LAPACK dense solves, not our tiled kernels. Blocking changes
    summation order and therefore error growth.
  * Single random instance per configuration with a fixed seed. Indicative of
    the mechanism, not a distribution over problems.
  * Does NOT establish silicon behaviour, only numerics.
