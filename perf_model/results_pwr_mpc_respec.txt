PWR-MPC RESOLUTION — re-specification, 16-bit operands, MCU-class tier
====================================================================================================
Evidence classes: [MEAS] measured, [CITE] cited literature, [EST]
estimate, [DER] derived from another model figure. All latency/energy/area
figures are MODELLED ESTIMATES at a 16nm-class node, +/-2x, NOT QUOTABLE.

====================================================================================================
(1) IS PWR-MPC THE RIGHT BENCHMARK FOR ITS SOCKET?  Answer: NO — re-specified
====================================================================================================

The deployed-practice case, all [CITE] (URLs at the end):

  a. Direct / finite-control-set MPC is the dominant formulation in power
     electronics. Karamanakos-Liegmann-Geyer-Kennel (IEEE OJIA 2020):
     "direct MPC for power electronics is most often formulated as an"
     "IQP. The common practice for solving such optimization problems in"
     "embedded control systems is with exhaustive search."
  b. The horizon is SHORT because enumeration is exponential: "Since the
     problem is NP-hard, such an approach is impractical for horizons
     longer than one step (Np > 1)." For a three-phase two-level converter
     with U = {-1,1}^3 the candidate count is 2^(3*Np) — 8 at Np=1, 64 at
     Np=2; a three-level converter gives {-1,0,1}^3 = 27 and 729.
  c. The SAMPLING RATE IS HIGHER THAN THE ROW ASSUMED, not lower. Direct
     MPC needs fs about two orders of magnitude above the switching
     frequency; published implementations use Ts = 5, 10, 25, 100 and
     125 us. The commercial reference point — MPDTC embedded in ABB's
     medium-voltage drive control software — is Ts = 25 us, i.e. 40 kHz.
     **The v1.1 row's 20 kHz was BELOW deployed practice.**
  d. Continuous-control-set MPC does exist here (indirect MPC with a
     carrier-based modulator, solved with qpOASES/ODYS, and miOSQP for the
     integer problem) but the published implementations run on dSpace-class
     rapid-prototyping hardware. It is a real but smaller socket.
  e. Explicit MPC (offline piecewise-affine + point location + table
     lookup) is the other deployed answer and is NOT a compute workload at
     all — it is a memory workload. We should concede it, not model it.

RE-SPECIFICATION (BENCHMARKS.md #3, v1.2): three-level NPC, |U| = 27,
Np = 2 exhaustive (729 sequences), n_x = 4, n_y = 2, Ts = 25 us / 40 kHz,
fp32. Retired definition retained off-set as PWR-CCS.

Np = 2 is chosen deliberately over the Np = 1 that ships today: Np = 1 is
modelled too (PWR-FCS1) and is a case we LOSE. Np = 2 is the capability the
literature says needs an FPGA or a branch-and-bound sphere decoder, so it is
the only version of this socket where an accelerator has an argument at all.

What the re-spec does to the row, at the recommended CM-100 [DER]:

row        algo   deadline    CM us  ofwhich   CPU us  speedup   perf/W  wc margin  desc mgn  binding resource
--------------------------------------------------------------------------------------------------------------
PWR-CCS    admm       50.0     4.29    0.80o     4.63    1.08x    15.2x      1.71x     1.27x  gemv_bw
PWR-MPC    fcs        25.0     1.61    0.80o     1.00    0.62x    23.5x      7.76x     6.76x  call_overhead
PWR-FCS1   fcs        25.0     0.85    0.80o     0.10    0.12x     7.1x     14.73x     0.61x  call_overhead
PWR-FAST   fcs        10.0     0.88    0.80o     0.15    0.16x    10.3x      5.67x     0.69x  call_overhead
PWR-FUSE   fcs        25.0     1.15    0.80o     0.52    0.46x    14.0x     10.89x     3.86x  call_overhead

  'ofwhich ...o' = the per-call invocation overhead component of CM latency.
  'wc margin' = worst-case-iteration latency against 50% of the control
  period. 'desc mgn' = datapath cycles per descriptor against the >= 8 rule.

THE HEADLINE IS NOT FAVOURABLE, and the flattering reading has to be killed
first. The hoped-for result was that enumeration, being embarrassingly
parallel and not bandwidth-bound, would move this row above parity. Both
halves of that are wrong:

  * LATENCY GETS WORSE, not better: 1.08x -> 0.62x. The re-specified row is ~1.6x SLOWER than the fastest CPU baseline, because
    the whole tick is 0.81 us of compute against a
    0.80 us invocation overhead, while the CPU pays no
    invocation cost at all. **Binding resource: per-call overhead, and
    below it the vector unit.** No amount of MAC array or bandwidth moves it.
  * IT IS STILL BANDWIDTH-BOUND, for a new reason. The candidate set IS a
    batch dimension, so the work is genuinely matrix-MATRIX — but the reuse
    depth is set by n_y = 2, THE NUMBER OF CONTROLLED OUTPUTS, not by the
    tile. Arithmetic intensity is 2.33 B/MAC against
    0.67 B/MAC for a tile-limited
    GEMM, so the batch buys a 1.7x traffic cut over pure GEMV, not the ~12x
    the array size suggests. The GEMM bandwidth ceiling had to be ADDED to
    the model for this to be expressible: it previously bounded only GEMV.

What the re-spec DOES buy, and it is worth more than the ratio:

  * The deadline stops being interesting. 7.8x margin against 50% of a 25 us period, and the op count is FIXED — no
    convergence tail, worst case == typical case. Determinism as strong as
    the EKF's, on the row where determinism is most saleable.
  * The codegen margin problem dissolves: 1.27x -> 6.76x against the >= 8-cycles-per-descriptor rule,
    because 16 descriptors of which 8 chained becomes 12 of which 0.
  * There is NO dependency chain. No Cholesky, no triangular solve, no
    loop-carried scalar. Dependency drain goes 64 -> 0 cycles.

====================================================================================================
(1b) THE CASE WE LOSE, reported because a model that cannot lose is not evidence
====================================================================================================

One-step FCS-MPC (27 candidates, 40 kHz) — what an MCU ships TODAY:
  CM 0.85 us (0.05 compute + 0.80 overhead) vs CPU 0.10 us = 0.12x
  perf/W 7.1x — above the 5x kill criterion but the lowest
  in the whole solver set, because the workload is smaller than the fixed
  overheads it has to amortise.
  Descriptor margin 0.61x — **BELOW the >= 8 codegen rule**.
  The two-level 100 kHz variant is 0.69x, also below.

  So the thinnest-codegen-margin problem does not vanish, it MOVES: the
  frozen row improves to 6.7x, and two adjacent real configurations of the
  same socket sit under the bar. The rule is not violated by the benchmark
  we chose; it is violated by the smaller ones next to it. Honest reading:
  **for one-step FCS-MPC, tell the customer to use the MCU.** The minimum
  viable version of this socket is a multi-step horizon.

====================================================================================================
(2) WOULD 16-BIT OPERANDS FIX THE LATENCY?  Partly — and it changes the format
====================================================================================================

Numerical basis, all [MEAS] (perf_model/results_precision_study.txt, C3/C4;
measured numerics, NOT silicon). Relative error in the commanded control
action against the fp64 solution of the SAME problem:

    fp32 operands, fp32 solve  (CM-100 today)   8.2e-07
    fp16 operands, fp32 solve  (the proposal)   1.9e-03
    bf16 operands, fp32 solve  (bf16 array)     1.9e-02
    fp64 operands, bf16 SOLVE                   6.1e-02

  Three things follow, and the second is the load-bearing new one:
  * fp16 beats bf16 by 10x at the same width. Mantissa bits dominate for
    these matrices — the OPPOSITE of the ML tradeoff that makes bf16 the
    default. **The array's bf16 specification is wrong for the solver path.**
  * KEEPING THE SOLVE AT fp32 COSTS NOTHING: fp16-operands/fp32-solve and
    fp16-operands/fp64-solve score IDENTICALLY (1.946e-03 both). The earlier
    study only ever paired 16-bit operands with an fp64 solve, which no CM
    SKU offers on the ADMM path, so the proposal was untested until now.
    The operand precision, not the solve, is what limits the mixed scheme.
  * FCS-MPC is far more tolerant (C4, 729 sequences, 200 trials): fp16
    changes the selected switching sequence on 3.0% of ticks at a mean
    excess cost of 1.5e-06 of the candidate cost spread; bf16 changes 11.0%
    at 9.2e-05. Because the output is a discrete argmin, a disagreement
    between two near-equal candidates is not an error. **Different algorithm,
    different precision floor — which is a MACIF fact, not a nicety.**

Modelled effect [DER]. fp16 operands, fp32 accumulate, triangular solve at
fp32 (its share of GEMV work is carried as `solve_prec_frac`):

row                          CM us  speedup    CM uJ   perf/W  wc margin  binding
---------------------------------------------------------------------------------
QUAD/fp32 (today)            35.96    1.74x    5.463    14.1x      2.93x  gemv_bw
QUAD/fp16 operands           24.07    2.60x    3.051    25.3x      4.40x  gemv_bw
QUAD/fp16 incl. SOLVE (bad)     22.14    2.82x    2.658    29.0x      4.79x  gemv_bw
PWR/fp32 (today)              4.29    1.08x    0.359    15.2x      1.71x  gemv_bw
PWR/fp16 operands             3.69    1.26x    0.237    22.9x      2.04x  gemv_bw
PWR/fp16 incl. SOLVE (bad)      3.47    1.33x    0.193    28.2x      2.19x  seq_overhead

  The third variant is listed so the trade is visible, NOT recommended:
  narrowing the triangular solve too costs 6.1e-2 control-action error (C3),
  ~30x worse than fp16 operands alone, for a further 1.06-1.09x of latency.

  QUAD-MPC: latency 35.96 -> 24.07 us (1.49x), energy 5.463 -> 3.051 uJ (1.79x), speedup 1.74x -> 2.60x
  PWR-CCS: latency 4.29 -> 3.69 us (1.16x), energy 0.359 -> 0.237 uJ (1.51x), speedup 1.08x -> 1.26x

  WHY IT IS ONLY ~1.3x AND NOT 2x, which is the adversarial point: halving
  operand width doubles the GEMV rate, but the GEMV term is not the whole
  iteration. Once it halves, the VECTOR UNIT becomes co-binding — ADMM's
  projection, dual update and over-relaxation are a fixed element-op count
  that 16 fp32 lanes cannot narrow. The dependency drain does not narrow
  either. **A bandwidth-bound row stops being bandwidth-bound before the
  bandwidth doubling is spent.** Same shape as the 128 B/cycle finding.

  Energy is the better half of the answer: operand bytes halve AND the
  multiplier drops 0.60 -> 0.20 pJ [EST], and neither is capped by the
  vector unit.

  DOES IT MOVE THE ROW ABOVE PARITY? Reported precisely, because this is
  where a flattering answer would hide:
    PWR-CCS: 1.08x -> 1.26x
    QUAD-MPC: 1.74x -> 2.60x
    But note what the CPU-side correction below did to the SAME question,
    and read the two together before quoting either.

  A CPU-BASELINE CORRECTION LANDED IN THE MIDDLE OF THIS AND MOVES THE RATIO
  IN OUR FAVOUR, so it is flagged, not banked. `model_cpu` charged
  ELEMENTWISE work at the outer-product rate, i.e. it ran min/max and
  horizontal reductions on SME2's ZA tile, which cannot execute them. The
  measured M4 gap is 2008 GFLOP/s FMOPA against ~250 GFLOP/s for streaming
  SVE — 8x. The model now carries `simd_flops_per_cycle = 32` for the SME2
  baseline, HALF the matrix rate rather than the measured eighth, i.e. the
  value least favourable to us. Effect on the retired ADMM row:

    simd=   64 FLOP/cyc  PWR-CCS speedup  0.97x   (uncorrected (elementwise on the ZA tile))
    simd=   32 FLOP/cyc  PWR-CCS speedup  1.08x   (corrected, generous  <-- adopted)
    simd=    8 FLOP/cyc  PWR-CCS speedup  1.72x   (corrected, measured M4 ratio)

    **So the famous 0.974x was partly an artefact of a CPU-side modelling
    error.** Corrected at the generous setting the retired row is at or just
    above parity. That is not a win — it is a row sitting exactly on a
    modelling assumption, and the honest instruction is that NEITHER 0.97x
    NOR 1.08x is quotable. What is quotable in shape: on this workload class
    we are at parity with a modern vector CPU and win on energy.

  VERDICT ON (2): adopt fp16 as the 16-bit solver operand format and make it
  a declared MACIF format. It is worth **1.16-1.49x latency and 1.51-1.79x
  energy** on the ADMM rows (PWR-CCS / QUAD-MPC respectively) at ~2400x the
  operand error — 8e-7 -> 1.9e-3 relative in the commanded control action.
  0.2% error in a commanded current is plausibly fine for a drive and is NOT
  obviously fine for a system whose constraint is a hard current limit, so
  this is a per-problem codegen OPTION a customer opts into, not a default.
  It does not rescue any row's parity position on its own: the re-specified
  PWR-MPC row is not bandwidth-bound in the first place, so fp16 does
  essentially nothing for it, and PWR-CCS moves only 1.08x -> 1.26x.
  The energy number is the one worth having: QUAD-MPC perf/W 14.1x -> 25.3x.

====================================================================================================
(3) THE MCU-CLASS CONTRADICTION — settled, and CLAUDE.md's framing is wrong
====================================================================================================

The contradiction: PHASE0_FINDINGS §4 credits zero-copy with 1.9x on this
row and with deciding its deadline feasibility; §5.1 records that in MCU
class there is no DRAM and no cache, so zero-copy and residency have
nothing to bite on. Both cannot be true.

The resolution is that the 25 us T0 constant was never an MCU-class number.
Decomposed [EST], each term naming a mechanism that can be measured alone:

  term                               T0       T1      T0M      T1M
  driver / RTOS API                8.00       --     1.50       --
  buffer map + pin                 6.00       --       --       --
  cache clean + invalidate         6.00       --       --       --
  IRQ + scheduler wakeup           5.00       --     0.50       --
  descriptor write                   --     0.10       --     0.10
  doorbell store                     --     0.10       --     0.05
  completion poll / latency          --     0.60       --     0.15
  TOTAL us                        25.00     0.80     2.00     0.30

  TWO of T0's four terms — buffer map/pin and cache maintenance — are
  artefacts of an MMU and a cache. An all-SRAM MCU has neither. What is left
  is an RTOS API call and an interrupt, and T1M is CHEAPER than T1 because
  there is no coherence round trip either.

  So the honest ablation on an MCU-class host [DER]:

row               T1        T0       T1M       T0M   T1/T0  T1M/T0M  T0M meets?
-------------------------------------------------------------------------------
PWR-MPC         1.61     25.93      1.11      3.28  16.09x    2.95x  MEETS
PWR-CCS         4.29     29.86      3.79     10.97   6.96x    2.90x  MEETS
QUAD-MPC       35.96     76.31     35.46    101.79   2.12x    2.87x  MEETS
EKF-24          2.58     28.06      2.08      8.91  10.89x    4.29x  MEETS

  And the energy side, where the answer is starker [DER]:

  row               T1        T0       T1M       T0M  T1/T0 uJ  T1M/T0M
  PWR-MPC        0.056     0.429     0.048     0.081     7.71x    1.70x
  PWR-CCS        0.359     0.843     0.347     0.465     2.35x    1.34x
  QUAD-MPC       5.463     7.297     5.444     6.562     1.34x    1.21x
  EKF-24         0.188     0.667     0.179     0.291     3.55x    1.63x

ANSWERS, in the order asked:

  Q: For an MCU-class host with on-chip SRAM only, what does the T1
     zero-copy tier actually buy?
  A: On the re-specified row, 2.95x latency and 1.70x energy — against 16.09x and 7.71x
     on a rich host. **Nearly all of what remains is invocation overhead,
     not data movement.** The data-movement half really does collapse, and
     for two independent reasons: the bytes are cheap (an on-chip copy at
     ~1.2 pJ/B [EST] instead of ~12 pJ/B of LPDDR) and there are barely any
     (716 B of persistent state for FCS-MPC, versus
     8400 B for the retired ADMM row and 102400 B for QUAD-MPC).
     CLAUDE.md's 'zero-copy and residency are VOID in MCU class' is right
     about residency and about coherency, and WRONG to bundle invocation
     overhead in with them.

     Decomposing the T1M-over-T0M advantage on the re-specified row, which
     is the crux of the whole question [DER]:
       total T1M advantage                  2.17 us
       of which invocation overhead         1.70 us  (78%)
       of which avoided on-chip copy        0.47 us  (22%)
     So on MCU class the advantage is ~4/5 invocation protocol and ~1/5 data
     movement, and the data-movement fifth exists only because an MCU bus is
     narrow, not because the bytes are far away.

  Q: Is the per-call overhead difference really descriptor/doorbell/syscall
     cost rather than data movement?
  A: YES, structurally — `call_overhead_us` is a fixed launch cost that the
     model charges independently of `bytes_moved`, and the decomposition
     above shows which terms survive the removal of DRAM. But the honest
     magnitude is much smaller than the headline: the advantage falls from
     31x (25/0.8) to 6.7x (2.0/0.30), and in ABSOLUTE terms from 24.2 us to
     1.7 us. Against a 25 us period that is 6.8% — real, not decisive.
     Against the 5 us period of the fastest deployed direct MPC (Ts = 5 us)
     it is 34%, and there it IS decisive. **The invocation-overhead pitch
     for MCU class is rate-dependent, and it needs 100 kHz+ to carry a
     deadline argument.**

  Q: So what buys PWR-MPC its deadline on an MCU-class host, and does the
     row still meet it?
  A: It meets it in EVERY tier, including T0M (3.28 us against
     25 us). Nothing 'buys' the deadline — the re-specified workload is
     ~640 cycles of arithmetic and the deadline was never the issue. What
     the CM buys on an MCU-class host is (a) energy per solve, (b) a bounded
     worst case with no iteration tail, and (c) offloading the control core.
     **The zero-copy argument should be withdrawn from the MCU-class pitch
     entirely** and replaced with low invocation overhead + determinism +
     energy. Zero-copy stays a real differentiator on rich hosts (QUAD-MPC,
     ARM-MPC, the ML rows), where DRAM and cache maintenance exist.

  ADVERSARIAL NOTE, because this cut the other way and should not be buried:
  an MCU-class integration is WORSE for us on one axis the previous analysis
  never charged. If the CM addresses host SRAM directly (the D2/D3 tightly-
  coupled story) it inherits the host's bus width — 8 B/cycle at 200 MHz is
  1.6 GB/s [EST], 4x LESS than the LPDDR path it replaces. The data is
  closer and the pipe is narrower. That is fine for a 716-byte FCS-MPC
  working set and it is NOT fine for anything that streams. Any MCU-class
  SKU must keep its own scratchpad, which means the copy does not disappear
  — it just becomes cheap.

====================================================================================================
MICROARCHITECTURE CONSEQUENCES — what actually changes in the design
====================================================================================================

1. INVOCATION OVERHEAD IS THE BINDING RESOURCE, and inside the datapath it
   is the VECTOR UNIT. Per-tick cycles at CM-100 [DER]:
     gemm_bw           124.0 cycles
     gemv_bw             0.5 cycles
     vector            524.8 cycles
     call_overhead     640.0 cycles
   Cost evaluation and argmin are 525 of 649 datapath
   cycles (81%); the invocation overhead is another 640 cycles on top,
   i.e. HALF the end-to-end latency.

   AN EARLIER DRAFT OF THIS SECTION HAD A UNIT ERROR AND THE CORRECTION
   CHANGES THE RECOMMENDATION, so it is recorded. It claimed the CM was 5x
   under-provisioned on elementwise throughput versus SME2, by comparing 16
   lanes/cycle against an SME2 figure counted in FLOPs. In the same units:

     CM-100, 16 lanes @ 800 MHz         12.80 G element-ops/s
     Cortex-A55                     1.50 G element-ops/s (1.0/cyc @ 1500 MHz)
     Cortex-A78                     4.80 G element-ops/s (2.4/cyc @ 2000 MHz)
     Cortex-A720                   12.32 G element-ops/s (5.6/cyc @ 2200 MHz)

   **We are at PARITY with the SME2 baseline on elementwise throughput, not
   5x behind.** The correct decomposition of why the row loses:

     CM datapath only          0.812 us   -> 1.24x vs the fastest CPU
     CM + T1M overhead (0.30)  1.112 us   -> 0.90x
     CM + T1  overhead (0.80)  1.612 us   -> 0.62x

   The CM COMPUTES this tick 1.24x faster than an SME2 core and then pays
   0.8 us to be asked. **For a sub-microsecond workload, no invocation
   protocol that involves a descriptor and a completion notification puts an
   accelerator ahead of the host core on latency** — even the MCU-class
   0.30 us tier only reaches 0.90x. That is an integration-depth statement,
   not a datapath one: this socket wants D3 (in-pipeline coupling) or it
   wants to be sold on energy and offload alone. Recommend the latter, and
   note it agrees with the settled finding that the advantage is energy.

   Two datapath responses remain worth having for their energy effect and
   for the descriptor margin; the second is far cheaper than the first:

    lanes  fp64 FMAs  PWR-MPC us  speedup  core mm2   d mm2
        8          4        2.27    0.44x     0.626  -0.072
       16          8        1.61    0.62x     0.698  +0.000
       32         16        1.28    0.78x     0.842  +0.143
       64         32        1.12    0.90x     1.128  +0.430

   (a) More lanes. 16 -> 32 costs +0.143 mm2 (+20% of the core) and buys
       1.26x on this row, because the merged-FMA construction doubles the
       fp64 cluster with it and because half the latency is not datapath.
       REJECTED on that ratio.
   (b) TWO ACCUMULATOR FEATURES that fold the two largest vector terms into
       the array at near-zero area: BROADCAST/BIAS INITIALISATION of the
       accumulator (folds the B@U broadcast-add) and SQUARE-ACCUMULATE
       (folds the ||r||^2 cost reduction). Modelled as PWR-FUSE:
         vector cycles   525 -> 154
         CM latency      1.61 -> 1.15 us  (datapath 0.81 -> 0.35)
         vs fastest CPU  0.62x -> 0.88x
         CM energy       0.0557 -> 0.0487 uJ (1.14x)
         descriptors     12 -> 9, descriptor margin 6.76x -> 3.86x
       NOTE ON HOW THIS IS SCORED, because the obvious way is wrong: the
       fusion is a CM DATAPATH capability, not a change to the algorithm, so
       the CPU still executes those vector ops. The comparison above is
       therefore CM(fused) against CPU(unfused). Scoring PWR-FUSE against a
       CPU running PWR-FUSE — which the table further up does — credits the
       CPU with an accumulator it does not have and makes the feature look
       like a regression. Read the table row for the CM column only.
       **RECOMMENDATION: (b), and it is a MACIF-boundary question** — a
       broadcast-initialised, square-accumulating accumulator is a property
       of the swappable macro, so it belongs in MACIF v0 alongside
       `accumulator_width[format]`. It is also the same L0-staging argument
       already flagged as the highest-value model extension: fold work into
       the accumulator at O(1) area instead of buying O(T^2) of array.

2. THE ARRAY BANDWIDTH CEILING IS NOW MODELLED, and it binds on exactly one
   row. Before this change the model applied a bandwidth bound only to
   GEMV, so it was structurally incapable of reporting a bandwidth-starved
   GEMM. A test asserts the new term binds on PWR-MPC and on nothing else,
   so it is neither decoration nor a silent perturbation of the other rows.

3. fp16, NOT bf16, IS THE 16-BIT SOLVER FORMAT. bf16 remains correct for
   ML. This makes the array multi-format on the 16-bit path and it is a
   declared MACIF capability, not an implementation choice — a macro that
   silently substituted bf16 for fp16 would cost 10x the control-action
   error and the runtime must refuse it, exactly as it refuses a missing
   fp64 path.

4. BANDWIDTH-FIRST SURVIVES, with a third mechanism. It was argued from
   batch-1 GEMV (no reuse) and from bank-geometry energy. FCS-MPC adds:
   even a workload with a real batch dimension can be operand-fetch-bound
   if its REUSE DEPTH is set by a problem dimension (n_y = 2) rather than
   by the tile. That is a stronger and more general statement than 'batch-1
   solvers have no reuse'.

WHAT WOULD FIRM THIS UP, in order of value per day
====================================================================================================
  1. Confirm the FCS-MPC parameter set against a real deployed controller
     (n_x, n_y, Np, Ts, |U| and whether a terminal cost or move-blocking is
     used). Everything in (1) hangs on the shape being right, and the shape
     is CITED literature, not a measured deployment.
  2. Measure a C2000 CLA or AURIX PPU task dispatch latency. The whole
     MCU-class answer rests on T0M = 2.0 us and T1M = 0.30 us, both [EST],
     and it is a half-day measurement on a launchpad board.
  3. Measure FCS-MPC on an F28379D and on an A78/SME2 board. The CPU side
     of this row is now the dominant uncertainty, and the elementwise-rate
     correction above shows the CPU model can move a verdict by 10%.
  4. Re-run C4 across plant families and switching-set sizes. One plant
     family with a fixed seed established the mechanism, not a distribution.
