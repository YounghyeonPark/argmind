============================================================================================================
AXIS 1 — MAC ARRAY.  Wall: the array is already 2.25x oversized for its
         own bandwidth. It pays on ENERGY (reuse depth) and on ML LATENCY.
============================================================================================================

The balance rule, derived not swept: a GEMV consumes one matrix element per
MAC, so its ceiling is bw/elem MAC/cycle; the array supplies tile^2*scale.
  min tile for a given fp32 GEMV bandwidth = sqrt(bw/2)
 bw B/cyc  min tile  min MACs   tile 12 binds above
       16       2.8         9                    no
       32       4.0        16                    no
       64       5.7        36                    no
      128       8.0        64                    no
      192       9.8       100                    no
      256      11.3       144                    no
      288      12.0       144                    no
      384      13.9       196                   yes
      512      16.0       256                   yes
     1024      22.6       529                   yes
  -> tile 12 (144 MACs) absorbs GEMV up to 288 B/cycle, and
     the SAME number at fp32, bf16 and int8 -- not a coincidence worth
     hiding: the array's rate multiplier happens to be ~1/element-size on
     this datapath (fp32 half-rate 4 B, bf16 full-rate 2 B, int8 double-rate
     1 B), so tile^2 * scale * elem is invariant. The GEMV balance point is a
     property of the ARRAY, not of the precision, which is convenient: one
     number sizes it for every format.
  -> CM-100 runs 128 B/cycle, so the array has 2.25x MAC headroom over the
     bandwidth it is fed. THAT is why '16x more MACs bought zero' held: the
     statement is about 64-128 B/cycle, not about arrays in general.

  QUADx is the worst-case speedup over the previous row; mm2/x is the area
  paid per unit of that speedup (mm2 / (ratio - 1)) -- a marginal cost, so
  smaller is better and the column is directly comparable step to step.
  16 -> 256 B/cycle returns a near-perfect 1.84-1.99x PER DOUBLING, at a
  marginal cost rising 0.020 -> 0.169 mm2 per x. 256 -> 512 returns 1.19x at
  1.682 mm2 per x -- TEN TIMES worse value -- because the fp32 GEMV ceiling
  (bw/4) crosses the 144-MAC array rate (72 MAC/cycle) at 288 B/cycle.
  Past there bandwidth alone buys nothing; you must buy array AND lanes AND
  banks together, which is a different part rather than a wider one.

  -> The ADMM and EKF rows are so GEMV-dominated that 4 lanes suffice to
     256 B/cycle. FCS-MPC needs 16 AT EVERY BANDWIDTH -- it is the one row
     where the vector unit binds first, which is the same fact the
     accumulator-fusion finding rests on (broadcast_init + square_accumulate

     lanes costs +0.143 mm2 for 1.26x). Lanes are provisioned for FCS-MPC and
     for ML, not for the solver rows.

  BANK-COUNT WALL, stated as the licensee sees it. The >=64-bit bank-word
  rule caps banks at bw/8, and the sizing run caps banks at 16 because the
  read crossbar and per-bank queues grow faster than the energy benefit:
      128 B/cycle -> 16 banks x   8 B word, read bus  1382 bits incl. addr/ECC
      256 B/cycle -> 16 banks x  16 B word, read bus  2764 bits incl. addr/ECC
      512 B/cycle -> 16 banks x  32 B word, read bus  5529 bits incl. addr/ECC
     1024 B/cycle -> 16 banks x  64 B word, read bus 11059 bits incl. addr/ECC
  512 B/cycle is a 5530-bit read bus into a 16 x 32 B scratchpad. That is
  a hard macro in disguise: no soft-IP licensee will floorplan it, and it
  is rejected on integrability, not on model output.

  SOLVER ENERGY IS MONOTONE INCREASING IN CAPACITY ACROSS THE WHOLE RANGE.
  There is no capacity at which the part gets cheaper to run. Bigger banks
  raise the cost of EVERY access, and the byte count a workload fetches does
  not change.

  The decisive case, and it confirms an earlier finding by a second route:
    ARM-MPC at 192 KB: 323.2 KB footprint OVERFLOWS, streams 135 KB, 25.23 uJ
    ARM-MPC at 384 KB: FITS, streams 3 KB, 26.34 uJ
    -> making it fit costs +1.11 uJ (1.044x) and +0.228 mm2,
       for ZERO latency benefit (ARM-MPC runs at 250 Hz with 5.5x margin).
       The pJ/byte penalty on every access exceeds the DRAM traffic it saves.

  RULE: size capacity to the FASTEST determinism-critical resident working
  set, and to nothing else. A slow loop that overflows should overflow.
  Capacity is a fitting constraint, so it belongs in the SKU table as a
  discrete choice, never in a scaling roadmap.

AXIS 4 — FREQUENCY AND PROCESS NODE.  Cheapest on paper; three real walls.
============================================================================================================

Wall 1: bitline length. Single-cycle read forces rows <= ~256*(800/f).
Wall 2: supply. Dynamic energy goes as V^2, so past nominal the part gets
        FASTER AND LESS EFFICIENT -- the opposite of the value proposition.
Wall 3: pipeline depth. A deeper datapath raises `drain_cycles`, and 97-100%
        of the sequencer's latency cost is dependency drain.

     should be presented to a licensee as a DOWNWARD energy knob with a

  PROCESS NODE is not a competitive axis at all, and this is the honest
  point. Every perf/W figure here is a RATIO against a CPU baseline. Moving
  from 16nm to 5nm moves the CPU too. Node buys absolute power and area for

  Node is a COST axis, not a scaling axis. Do not put it on a roadmap slide
  as though it improved the argument.

============================================================================================================
AXIS 6 — SCALING DOWN.  Where offload stops making sense, as a rule a
         customer can apply with two numbers they already have.
============================================================================================================

Derivation. speedup = cpu / (compute + overhead). With k = cpu/compute:
      speedup >= 1  <=>  cpu >= overhead * k/(k-1),   impossible if k <= 1
The floor is a ratio between the LAUNCH PROTOCOL and the DATAPATH ADVANTAGE.
It is not a MAC count and not a problem dimension.

============================================================================================================
MULTI-CM — is it a product or a distraction?
============================================================================================================

Q1. Can a SINGLE solve be split? The iteration is loop-carried, so there is
    no iteration-level parallelism. But there IS work-level parallelism
    inside an iteration: row-split every GEMV, each CM owning a row block.
    The cost is a BARRIER AT EVERY CHAIN STEP, because the next step's
    operand is the concatenation of this step's partials. MEASURED chain
    depth of one checked ADMM iteration = 17 steps under wait-mask
    semantics (32 under v0 one-token semantics).

    Charged GENEROUSLY to the multi-CM case: perfect load balance, zero
    broadcast bytes, no row-quantisation waste, capacity always sufficient.

 n_CM    sync model  sync us/iter  per-iter us  QUADwc us  vs 1 CM
    1             -         0.000        3.157      235.2    1.00x
    2   shared_spad         0.340        1.919      142.8    1.65x
    2   tightly_cpl         2.550        4.129      306.3    0.77x
    2      coherent         8.500       10.079      746.6    0.32x
    4   shared_spad         0.340        1.129       84.4    2.79x
    4   tightly_cpl         2.550        3.339      247.9    0.95x
    4      coherent         8.500        9.289      688.2    0.34x

    ANSWER: two CMs make a single ADMM solve SLOWER than one at any barrier
    cost above ~16 cycles. Tightly-coupled mailbox loses (0.77x). Coherent-
    fabric synchronisation loses catastrophically (0.32x) -- and coherent is
    the only organisation that does not require new silicon.

    ** AND THE ONE ROW THAT WINS IS UNPHYSICAL, WHICH IS THE REAL ANSWER. **
    Read the `shared_spad` rows adversarially. They charge each CM 1/n of the
    datapath time WHILE SHARING ONE SCRATCHPAD. QUAD-MPC's binding resource
    is scratchpad read bandwidth (`gemv_bw`, see the reference table). Two
    datapaths behind ONE 128 B/cycle scratchpad on a bandwidth-bound row
    deliver 1.00x, not 1.65x -- the second datapath starves. The row is only
    reachable if the scratchpad bandwidth ALSO doubles, at which point the
    bandwidth is what bought the speedup and the datapath replication is
    incidental. Corrected, the honest table is:
        2 CM, shared scratchpad, bandwidth NOT scaled -> 1.00x (starved)
        2 CM, shared scratchpad, bandwidth doubled    -> that IS 1 CM at
                                                        256 B/cycle, cheaper
    So intra-solve multi-CM is not merely a bad trade; on the workload class
    that defines this architecture there is no mechanism by which it helps.

Q2. Quantifying that, because 'it is one wider CM' should be priced. Compare
    2 x CM-100 against 1 CM with the same total bandwidth:
    2 x CM-100        : 1.572 mm2, 2 x 128 B/cyc over TWO 192 KB scratchpads, QUAD-MPC wc 142.8 us (best-case barrier)
    1 x CM @256 B/cyc : 0.947 mm2, 256 B/cyc over ONE 192 KB scratchpad, QUAD-MPC wc 120.6 us
    -> the single wide CM is 1.66x CHEAPER in area and 1.18x FASTER.
    For bandwidth-bound work, buying bandwidth inside one CM dominates
    buying a second CM, and it is not close. Marginal cost of bandwidth:
      128 -> 256 B/cycle inside one CM: +0.161 mm2 for +128 B/cycle
      a second CM-100:                  +0.786 mm2 for +128 B/cycle
      -> 4.9x more area per byte/cycle via replication
    And at 4 CMs, even taking the unphysical shared-scratchpad row at face
    value, replication still loses on area:
      4 x CM-100        : 3.145 mm2, QUAD-MPC wc 84.4 us
      1 x CM @512 B/cyc : 1.268 mm2, QUAD-MPC wc 101.3 us
      -> replication is 2.48x the area for 1.20x the speed, i.e. 2.07x worse value --
         and 512 B/cycle is itself already rejected as unintegrable, so this
         comparison is between two options we decline, not a recommendation.

Q3. FCS-MPC's 729 candidates ARE independent. Does that parallelism want
    two CMs? THIS IS THE ONE PLACE THE ANSWER IS NOT AN IMMEDIATE NO, and it
    is worth saying so rather than reporting the convenient result.
    FCS-MPC compute is 0.812 us against a 0.8 us launch. It is 0.62x overall and the
    deficit is invocation, not datapath (datapath alone is 1.24x).
    Zero dependency chains, so a split needs exactly ONE barrier -- the
    cross-CM argmin reduction. The most favourable split in the whole set:
      2 CM, shared_spad  0.826 us vs 1.612 us single -> 1.95x datapath, 1.22x vs the fastest CPU (ABOVE parity)
      2 CM, tightly_cpl  0.956 us vs 1.612 us single -> 1.69x datapath, 1.05x vs the fastest CPU (ABOVE parity)
      2 CM, coherent     1.306 us vs 1.612 us single -> 1.23x datapath, 0.77x vs the fastest CPU (below parity)
    So yes: candidate splitting does convert 0.62x into ~1.2x parity. It is
    still the wrong purchase, for three reasons that must be given together:

    (a) NO DEADLINE NEEDS IT. FCS-MPC already meets its 25 us period at
        15.5x margin. The latency we would be buying is
        latency the customer does not have a use for; the socket is sold on
        energy (22.0x perf/W) and core offload.
    (b) IT IS THE WRONG BOTTLENECK. FCS-MPC is the one solver row where the
        VECTOR UNIT binds first, not scratchpad bandwidth -- it needs 16 lanes
        at every bandwidth in the sweep above. So the resource in short supply
        is vector lanes, and there are two cheaper ways to buy them:
          MACIF broadcast_init + square_accumulate: 525 -> 154 vector cycles,
            0.62x -> 0.88x, NEAR-ZERO AREA (already the settled answer)
          16 -> 32 lanes in one CM: +0.143 mm2 for 1.26x
          a second CM:              +0.786 mm2 for ~1.95x datapath
        Ranked by area per unit of speedup, the second CM is LAST of three.
    (c) IT DOUBLES STATIC POWER ON A ROW SOLD ON ENERGY. Two CM-100 instances
        leak twice as much for the same solve. Spending the energy claim to
        buy latency nobody asked for is the wrong trade on this row
        specifically, because energy IS the pitch here.
    NOTE the shared_spad row carries the same caveat as Q1: it charges 1/n
    datapath time behind one scratchpad. That is defensible HERE and not in
    Q1, because FCS-MPC is vector-bound rather than bandwidth-bound -- the
    replicated resource really is the scarce one. Stating why the same row is
    admissible on one benchmark and not the other is the whole point of
    tracking the binding constraint per row.

Q4. MANY INDEPENDENT LOOPS (a manipulator's joints, several estimators).
    This is the one case with a real argument, and it is NOT a parallelism
    argument -- it is capacity plus determinism isolation.

row          duty % wc  footprint KB  loops by duty  loops by capacity   binding
QUAD-MPC         23.52         138.8            4.3               1.38  capacity
ARM-MPC          18.26         323.2            5.5               0.59  capacity
PWR-MPC           6.45           0.7           15.5             274.29      duty
EKF-24            0.26           7.9          388.3              24.30  capacity
EKF-96            1.31         117.0           76.4               1.64  capacity

    CAPACITY BINDS CONSOLIDATION ON 4 OF 5 ROWS, by 0.1-47x.
    QUAD-MPC has 4.3x throughput headroom and 1.38x capacity headroom: one
    CM-100 can host ONE flagship MPC loop, not four. ARM-MPC does not even
    fit once. So the reason to instantiate a second CM is that the working
    sets do not co-reside -- which a bigger scratchpad also solves, at
    0.020 mm2 per 32 KB against 0.786 mm2 for a whole second CM.
    Note the direction of the error a throughput-only analysis would make:
    duty cycle says 'consolidate 4-388 loops', capacity says 'consolidate
    one'. Provisioning a shared accelerator from duty cycle alone would
    oversell consolidation by up to 47x.

    THE SECOND ARGUMENT IS JITTER, AND IT IS THE STRONGER ONE. Determinism
    is the product, so consider a drive node: FCS-MPC at 40 kHz (25 us
    period) sharing a CM with QUAD-MPC at 1 kHz.
      QUAD-MPC worst-case solve = 235.2 us = 9.4 periods of the 40 kHz loop.
      Non-preemptible at SOLVE granularity  -> the fast loop misses 10 deadlines. FATAL.
      Preemptible at DESCRIPTOR granularity -> worst-case blocking is the
      longest single descriptor. Measured longest in the ADMM DAG is a full
      A-product at ~1600 cycles = 2.0 us = 8.0% of a 25 us period. TOLERABLE.
    -> DESCRIPTOR-GRANULARITY PREEMPTION, not a second CM, is what makes
       mixed-rate consolidation safe. It is a sequencer/scoreboard feature
       (save the wait mask and token state, admit the higher-priority
       template) and it is nearly free next to a 0.79 mm2 replica.

VERDICT ON MULTI-CM
  * Intra-solve splitting: DEAD IN PRINCIPLE AND IN NUMBERS. Loses to one
    wider CM on both area and latency, at every barrier cost.
  * Candidate-batch splitting (FCS-MPC): the ONE case that works -- it does
    reach ~1.2x CPU parity. Rejected anyway, on three grounds together: no
    deadline needs it (15.5x margin), the scarce resource is vector lanes
    and two cheaper ways to buy them exist (MACIF accumulator fusion at
    ~zero area, then +0.143 mm2 of lanes, then +0.786 mm2 of CM), and it
    doubles static power on the row whose entire pitch is energy.
  * Many independent loops: bounded by CAPACITY and JITTER, both of which
    have cheaper fixes (more KB; descriptor-granularity preemption).
  * What survives: INDEPENDENT INSTANCES, NO INTERCONNECT, when a licensee
    wants hard physical isolation between safety domains (ASIL) or between
    control rates. That is ALREADY SUPPORTED -- it is instantiating the IP
    twice -- and it needs exactly one thing from us: the runtime API must
    address multiple devices. Nothing in RTL, no shared scratchpad, no
    CM-to-CM coherency, no one-sequencer-many-datapaths.
  * WHAT WOULD CHANGE THIS: a frozen-set row that (a) needs >288 B/cycle of
    fp32 GEMV to make a deadline, or (b) needs >384 KB resident at >1 kHz.
    Neither exists today. Re-open the question if one appears; until then
    'multi-core scaling' should come OFF the Phase 4 list, because keeping
    it there implies a verification obligation we have no reason to accept.

============================================================================================================
THE VERIFICATION TENSION — parameters are not free, so classify them
============================================================================================================

§5 markets 'parameterized (tile size, precisions, SRAM depth, bus type)'.
§9 flags 'few validated configs, not full matrix'. Both are right, and the
resolution is that PARAMETERS ARE NOT ALL THE SAME KIND OF PARAMETER.

REPLICATIVE — changes a width or a depth, reuses the same control FSMs.
Verification cost is a re-run of an existing regression at a new elaboration.
  tile / tile_n        generate-loop over MAC cells; reduction tree is
                       width-generic. Validated range 8-16, square only.
  vector_lanes         generate-loop over FMA slices. 8-32.
  scratchpad_kb        bank depth only. Re-run the memory compiler + timing.
  bank word bytes      >= 64 bits by design rule. 8-16 B.
  freq target          constraint-level, not RTL. Re-run timing closure.

STRUCTURAL — changes control logic, protocol behaviour, or a declared
contract. Each value is a SEPARATE verification target with its own
coverage closure. These are what must be rationed.
  n_banks              arbiter, address interleave, conflict resolution.
                       VALIDATE 8 AND 16 ONLY.
  precision set        MACIF declaration + the runtime's REFUSAL paths. A
                       macro without fp64, or with bf16 substituted for
                       fp16, must be refused at codegen. Each removal is a
                       new negative-test suite, not a smaller design.
  fp64 present         presence/absence changes the PRODUCT (no interior
                       point without it), not just the datapath.
  bus type             THE MOST EXPENSIVE PARAMETER IN §5 AND THE MOST
                       CASUALLY MARKETED. AXI4 / ACE-Lite / TileLink each
                       need their own protocol-checker verification and
                       their own coherency-behaviour proof. This is not a
                       parameter, it is three deliverables.
  seq queue depth      scoreboard + token-reuse hazard rule. FIX AT 8.
  chain block width    follows datapath width automatically. Not a knob.
  drain / pipe depth   timing-driven, but it changes the scoreboard's
                       hazard distances. FIX PER SKU, do not expose.

RULE: sell the replicative set as parameters. Sell the structural set as
a SKU list. Never print 'bus type' in a parameter list again.

  AND ONE PIECE OF GOOD NEWS THAT SHOULD BE STATED PLAINLY, because the fp64
  decision has been treated as a cost all along: in the merged multi-format
  cluster, fp64 THROUGHPUT UP TO lanes/2 IS FREE. The area is set by

  premium (+0.067 mm2 at 16 lanes over an fp32-only unit of the same width),

  ~9%-of-core decision taken once, not a scaling axis with a running cost.

  interior-point solve is allowed to touch DRAM and we should say so rather
  than size a scratchpad to hide it.

    CM-100S (16-MAC solver-only) saves 0.138 mm2 (18%) and costs
    2.68x the EKF-96 energy. EKF is a BEACHHEAD workload, so a
    SKU that is bad at state estimation is a SKU for a socket we are not
    selling into. The array is the cheapest thing in the part
    (17% of core). Do not spend a verification slot to remove it.
    -> tile stays a REPLICATIVE synthesis parameter over 8-16, unsupported
       outside that range. Not a SKU.

    CM-200 (256 B/cyc, 16x16, 256 KB) costs 1.42x the core for
    1.95x QUAD-MPC worst case and 1.18x solver energy, against
    deadlines that already have 4-14x margin. It is a real Pareto point and
    it has NO WORKLOAD IN THE FROZEN SET. Keep it as a documented synthesis
    configuration for a customer who brings a harder problem; do not
    verify it, do not price it, do not put it on a roadmap.

============================================================================================================
CUSTOMER-FACING ENVELOPE RULE — 'is my workload in the CM's band?'
============================================================================================================

Five tests. All must pass. Each uses a number the customer already has.

1. RESIDENCY. Sum every matrix as a DENSE RECTANGLE at your working
   precision, plus every working vector and temporary. Not packed
   triangular -- the address generators cannot express it.
     <= 192 KB (CM-100) or <= 64 KB (CM-50)  -> in.
   Over that, DRAM enters your control loop and the determinism claim is
   void. This is a hard edge, not a gradient.

2. LATENCY FLOOR. Measure your solve on your host core. Then:
     host time >= 5 us     -> the latency claim holds (T1, rich host)
     host time >= 1.7 us   -> holds on an MCU-class doorbell (T1M)
     host time <  1.5 us   -> USE THE CPU. No datapath size fixes this;
                              the launch protocol is the cost.
   (Derivation: cpu >= overhead*k/(k-1) with k = 1.2-2.2 measured.)

3. ENERGY FLOOR, which is LOWER than the latency floor -- most workloads
   that fail test 2 still pass this one:
     host time >= 0.4 us of an efficient in-order core -> >=5x perf/W
   Below that, the CM's static power during launch exceeds your whole
   compute energy. Requires power gating, which is mandatory anyway.

4. DESCRIPTOR DENSITY. Average >= 8 datapath cycles per descriptor, with
   no burst of more than 8 consecutive short descriptors. In practice:
   your inner-loop matrix/vector operations must average >= ~64 elements
   at 128 B/cycle fp32. Frozen-set rows run 238 cycles/descriptor (30x the
   bar); one-step FCS-MPC and 100 kHz two-level FCS-MPC FAIL it. Tell those
   customers to use the MCU.

5. OFF-CHIP TRAFFIC. (bytes that must cross the boundary per call) /
   (deadline) <= 6.4 GB/s at the baseline LPDDR4x provisioning. If your
   answer is a weight-streaming model, this is the ONLY test that matters
   and no on-chip parameter changes it.

AND THE REUSE-DEPTH DIAGNOSTIC, which tells you WHICH knob is yours:
  Take your dominant product. How many times is each fetched operand
  element consumed before it is discarded? Call it R.
    R = 1        pure GEMV. Bandwidth-bound. MAC count is irrelevant to you.
    R < 8        still bandwidth-bound even with a batch dimension
                 (FCS-MPC has R = n_y = 2 across 729 candidates and is
                  bandwidth-bound; the batch buys 1.7x, not 12x).
    R >= tile    tile-limited GEMM. This is the only regime where a bigger
                 array pays, and even then it pays in ENERGY first.
  If R is set by a PROBLEM dimension rather than by the tile, you are
  operand-fetch-bound. That is the general form of the batch-1 finding and
  it is the single most useful thing to tell a customer architect.

============================================================================================================
SUMMARY — the band, stated plainly
============================================================================================================

  axis                  scales?  usable range              wall, and what sets it
  --------------------  -------  ------------------------  ----------------------
  MAC array             weakly   36 - 256 MACs             energy return dies at 144;
                                                           ML latency wants 1024 but
                                                           then lanes bind
  scratchpad bandwidth  YES      64 - 256 B/cycle          16 banks x 16 B; and the
                                                           fp32 GEMV ceiling crosses
                                                           a 144-MAC array at 288
  capacity              NO       a discrete fit, 64/192KB  monotone energy cost; only
                                                           ever tracks the fastest
                                                           resident working set
  frequency             weakly   600 - 1000 MHz            bitline folds at ~1100;
                                                           V^2 destroys the energy
                                                           claim above nominal
  process node          NO       cost axis only            the CPU baseline moves too
  fp64 FMA count        YES      4 - 16                    linear on interior point,
                                                           and no customer needs it
  sequencer             NO       fixed                     97-100% is dependency
                                                           drain; only shrinks
  multi-CM              NO       independent instances     loop-carried iteration;
                                                           loses to one wider CM
  external bandwidth    n/a      a provisioning input      >=25 GB/s for 1.1B decode,
                                                           and undifferentiated there

  TWO axes scale usefully: scratchpad bandwidth (64 -> 256 B/cycle, ~4x) and
  the fp64 FMA cluster (4 -> 16, ~4x, on one benchmark that does not need it).
  Everything else is a fit, a cost, or a distraction. The honest product
  statement is a NARROW BAND -- roughly 3-4x of usable configuration span --
  and that is a legitimate position for control-domain IP, where the
  customer's problem sizes are set by physics and actuator counts rather
  than by a scaling roadmap. Two validated SKUs cover it.

  WHAT WOULD FALSIFY THIS: an L0 operand register file. It would buy the
  array's reuse at O(T) area instead of O(T^2), which drops the honest array
  size to 36-64 MACs AND raises the bandwidth at which the array starts to
  bind. That is the highest-value model extension outstanding and it moves
  two of the walls above.
