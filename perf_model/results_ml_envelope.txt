========================================================================================================
ARGMIND CM — THE ON-DEVICE AI ENVELOPE.  Two regimes, and the boundary
            between them, drawn with numbers.
========================================================================================================
ALL FIGURES MODELLED ESTIMATE, 16nm-class, +/-2x, NOT QUOTABLE EXTERNALLY.
EVERY perf/W BELOW IS vs A CPU BASELINE. For ML that is NOT the adversary a
customer cares about -- see section 5 before quoting any of it.
ACCURACY IS NOT MODELLED. int4 here is a statement about bytes and cycles.

========================================================================================================
THE ANSWER, UP FRONT
========================================================================================================

  1. THE PLANE HAS TWO BOUNDARIES SET BY TWO DIFFERENT RESOURCES.
     FEASIBILITY is set by external bandwidth and moves 8x across an 8x
     bandwidth sweep: 0.32 G int8 / 0.64 G int4 at 6.4 GB/s and 20 tok/s,
     rising to 2.56 / 5.12 G at 51.2 GB/s. DIFFERENTIATION (>=5x perf/W) is
     set by whether the working set is RESIDENT and barely moves at all:
     0.00021-0.00025 G int8 / 0.00066 G int4 across the same sweep. Buying
     bandwidth buys feasibility and buys ~nothing of differentiation.

  2. THE FEASIBLE-UNDIFFERENTIATED ZONE IS ~1000-1500x WIDE IN MODEL SIZE
     AND CONTAINS EVERY MODEL ANYONE WOULD CALL A LANGUAGE MODEL. The
     differentiated zone tops out at 0.2-0.7 M parameters, which is an MLP,
     not an SLM. int4 doubles both boundaries and lifts the perf/W plateau
     from ~2.5x to ~4.0x -- closer to the 5x bar, still under it at every
     point in the plane.

  3. THE INVARIANT IS EXTERNAL ARITHMETIC INTENSITY, ~2.6 MAC PER BYTE
     crossing the CM boundary. Batch-1 int8 decode is exactly 1.0 by
     construction and int4 decode is 1.93; ViT-Tiny is 223; a resident MLP
     policy is 258-989; QUAD-MPC is 1022. One number orders the whole set.

  4. THE HYBRID LOOP SURVIVES, BUT NOT AS AN ML CLAIM AND NOT AT 192 KB.
     Policy + solver co-resident fits 192 KB only for the smaller of two
     cited real policies, with 1.3% margin, and only because codegen
     exploits A = [I;Gamma]; the widely used legged-gym shape needs 256 KB at
     int4 or 384 KB at int8. End to end it is 1.8-2.3x latency and 9.6-12.2x
     energy against an NPU-plus-CPU split with the NPU charged ZERO -- but
     the network is only 1.1-4.0% of the tick, so THE HYBRID LOOP'S ADVANTAGE
     IS THE SOLVER'S ADVANTAGE. What it adds is one engine, one address
     space, one deterministic joint tick, and one fewer offload per tick.

  5. THERE IS NO RESIDENT-WEIGHT ML SKU. 4 MB of scratchpad holds 8 M int4
     parameters, ~80x short of what a 6.4 GB/s stream already delivers, while
     costing 6.3x core area and 2.2x solver energy. Killed twice over.

  6. AND THE PART THAT HURTS: EVERY ML perf/W FIGURE HERE IS AGAINST A CPU,
     WHICH IS NOT THE BASELINE A CUSTOMER WOULD DEPLOY. The ML
     inference-efficiency claim is UNSUPPORTED, not merely narrow. Section 5
     says what is left: arithmetic retargetability, co-residency plus a
     joint deterministic tick, and MACIF. None of the three needs an
     inference-efficiency comparison to stand up.

  7. ONE ARCHITECTURE CONSEQUENCE, AND IT AMENDS §8. int4's array knee is
     144 B/cycle, not the 288 that fp32/bf16/int8 share, because int4's rate
     multiplier is int8's while its element halves. 128 B/cycle is still
     under it, but §8's '256 B/cycle is a drop-in upgrade' does NOT hold at
     int4: that part wants a 16x16 tile, not 12x12.

========================================================================================================
(0) int4 SELF-AUDIT — the three ways this could have been a free win
========================================================================================================

Adding a precision plus a swept axis is the exact shape of change that
produced modelling errors 13 and 14 (an axis that looked free because the
model could not express its cost). Three checks, run mechanically:

  CHECK A: does int4 halve BANDWIDTH demand without granting free COMPUTE?
    int8:    1 B/elem, array    288 MAC/cyc, GEMV ceiling    128 MAC/cyc (= min(bw/elem, array))
    int4:  0.5 B/elem, array    288 MAC/cyc, GEMV ceiling    256 MAC/cyc (= min(bw/elem, array))
    -> ARRAY RATE IS IDENTICAL (288 MAC/cyc). A digital multiplier is sized
       by its WIDER operand, and weight-only 4-bit quantisation multiplies a
       4-bit weight by an 8-bit activation, so the array slot is unchanged.
       Only the fetch ceiling doubles, 128 -> 256 MAC/cyc, and it is still
       BELOW the array rate -- int4 GEMV remains bandwidth-bound on chip.

  CHECK A2, WHICH IS NOT A CHECK BUT A CONSEQUENCE, AND IT MATTERS FOR §8.
  §8's balance rule says a 12x12 array absorbs GEMV up to 288 B/cycle 'at
  fp32, bf16 AND int8, because this datapath's rate multiplier is
  ~1/element-size'. int4 BREAKS that coincidence: its rate multiplier is
  int8's while its element is half the size. The bandwidth at which the
  array starts to bind is `macs_per_cycle * bytes_per_elem`:
  prec   MAC/cyc  B/elem  array binds above  min tile @256 B/cyc
  fp32        72       4             288 B/c                11.3
  bf16       144       2             288 B/c                11.3
  int8       288       1             288 B/c                11.3
  int4       288     0.5             144 B/c                16.0
    -> at int4 the knee is 144 B/cycle, NOT 288. CM-100's 128 B/cycle sits
       just under it, so nothing changes today. But §8 sells 256 B/cycle as
       a DROP-IN upgrade on the strength of the array's 2.25x headroom, and
       AT int4 THAT HEADROOM IS GONE: a 256 B/cycle part wants a 16x16 tile
       for int4 GEMV, not 12x12. This is a real amendment to the balance
       rule and it is the one architectural consequence of adding int4.

  CHECK B: is DRAM energy still charged on every streamed weight byte?
    int8: moved   1139.9 MB, DRAM energy  13679.0 uJ of  16453.5 uJ total ( 83.1%)
    int4: moved    589.9 MB, DRAM energy   7079.0 uJ of   8570.1 uJ total ( 82.6%)
    -> YES, at the full 12 pJ/B, and it is the DOMINANT term in both. int4
       halves the bytes; it does not make a byte cheaper.

  CHECK C: is the ENERGY-PER-MAC credit for int4 small and does it matter?
    int4 MAC at 0.060 pJ [EST]:    8570.1 uJ
    int4 MAC forced to int8's 0.070 pJ:    8592.1 uJ (1.0026x)
    -> the int4 MAC-energy credit is worth <0.5% of the row. Every
       conclusion below is insensitive to it, because these rows are
       DRAM-dominated. That is the honest reason to accept the estimate.

  WHAT int4 IS NOT: expressible in the v0.1 descriptor format. Two int4
  elements share a byte, so a row length must be even and a leading
  dimension is a count of NIBBLES, while the v0.1 AGUs address bytes.
  Format.INT4 is also absent from the runtime's precision enum, so the
  simulator cannot hold an int4 buffer at all. Recorded as a REQUIREMENT
  with a cost, not quietly assumed -- the last two capacity errors were
  both 'the model assumed a layout the descriptor cannot address'.

========================================================================================================
(1) WHY THERE IS A BOUNDARY AT ALL — arithmetic intensity per EXTERNAL byte
========================================================================================================

The CM-100 scratchpad delivers 102.4 GB/s (128 B/cycle x 800 MHz).
An edge SoC offers 6.4-51.2 GB/s off chip. So for ANY workload that reads
each external byte once and does ONE MAC with it:

    compute_time / transfer_time  =  BW_external / BW_scratchpad

which is INDEPENDENT of model size AND of precision, because int4 halves
both sides. Write that ratio rho = BW_ext / BW_spad. With double buffering
hiding 80% of compute behind the stream, the DRAM share of the tick is
(1 - 0.8*rho) / (1 + 0.2*rho), and with no overlap at all it is 1/(1+rho):
 BW_ext GB/s      rho  no overlap  double-buffered
         6.4    0.062         94%            93.8%
        12.8    0.125         89%            87.8%
        25.6    0.250         80%            76.2%
        51.2    0.500         67%            54.5%
       102.4    1.000         50%            16.7%

  Against the model on the frozen 1.1B row. This is a CROSS-CHECK, not an
  illustration: the analytic line is derived from the bandwidth ratio alone
  and the model computes bytes, cycles and overheads independently.
 BW GB/s  wprec    model  analytic
     6.4   int8    93.8%     93.8%
     6.4   int4    93.8%     93.8%
    12.8   int8    87.7%     87.8%
    12.8   int4    87.7%     87.8%
    25.6   int8    76.1%     76.2%
    25.6   int4    76.0%     76.2%
    51.2   int8    54.3%     54.5%
    51.2   int4    54.2%     54.5%

  Agreement to ~0.5 point, and int4 sits on TOP OF int8 in every row. That
  is the whole point: HALVING THE WEIGHT WIDTH DOES NOT CHANGE WHICH
  RESOURCE BINDS, because it halves the on-chip and the off-chip demand by
  the same factor. int4 buys 2x of absolute throughput and 0x of regime.

  NOW THE OTHER REGIME. External-byte intensity, MACs per byte crossing
  the CM boundary per call, at the CM-100's own 6.4 GB/s:
row                     persistent KB  moved KB/call  MAC/ext byte  perf/W vs-CPU
SLM 1.1B int8 decode        1113386.8      1113203.8             1          2.29x
SLM 1.1B int4 decode         576277.4       576094.4         1.933          3.71x
SLM 0.1B int4 decode          57020.1        56832.1         1.862          3.62x
VIT-TINY (frozen row)          5566.4         5521.4         222.9         28.22x
POLICY-512 (resident)           190.1            0.2         989.3         18.68x
POLICY-256 (resident)            50.7            0.2           258         17.40x
QUAD-MPC (resident)             138.8            1.0          1022         12.33x

  THE BOUNDARY IS A RESIDENCY BOUNDARY, NOT A SIZE BOUNDARY. Everything
  whose persistent data FITS reads only its delta from off chip, so its
  external intensity is 1e2-1e3 MAC/byte and DRAM energy vanishes from the
  total. Everything that does NOT fit re-streams its weights every call at
  1-2 MAC/byte, and DRAM energy becomes 80-95% of BOTH sides of the
  comparison. perf/W does NOT go to 1.0 -- the shared DRAM term is added to
  a CPU core cost that also grows with parameter count, so it flattens onto
  a PLATEAU (2.3-2.7x at int8, 2.7-4.2x at int4 in the table below). The
  point is not that the plateau is 1.0; it is that THE PLATEAU IS BELOW 5x
  EVERYWHERE. int4 moves the size at which you fall off the cliff. It does
  not move the cliff, and it does not lift the plateau over the bar.

  TWO BOUNDARIES, TWO DIFFERENT RESOURCES. THAT IS THE WHOLE RESULT.
  ==================================================================
    FEASIBILITY is set by EXTERNAL BANDWIDTH and moves 8x across the sweep:
      int8 20 tok/s: 0.32 G at 6.4 GB/s -> 2.56 G at 51.2 GB/s (8.0x)
    DIFFERENTIATION is set by SCRATCHPAD CAPACITY and barely moves at all:
      int8 20 tok/s: 0.00021 G at 6.4 GB/s -> 0.00025 G at 51.2 GB/s (1.21x)
      int4 20 tok/s: 0.00066 G -> 0.00066 G (1.00x -- flat)
    Buying external bandwidth makes a bigger model FEASIBLE and does
    essentially nothing for whether it is DIFFERENTIATED. That is the
    quantitative form of 'we are not differentiated on a workload whose
    binding resource is off chip'.

    AND THE INVARIANT BEHIND IT, which is the number to keep: at every
    crossover point in the table the EXTERNAL ARITHMETIC INTENSITY is
    2-3 MAC per external byte, across an 8x bandwidth range and both
    precisions. THAT is the boundary, and it is a workload property, not a
    configuration property:

        DIFFERENTIATED  requires  >~ 2.6 MAC per byte crossing the CM boundary

    Check it against the rows in section 1: batch-1 int8 decode is exactly
    1.0 (one MAC per weight byte, by definition), int4 decode is 1.93,
    ViT-Tiny is 223, a resident MLP policy is 258-989, QUAD-MPC is 1022.
    One number orders every row in the set and it is neither MAC count nor
    model size.

    NOW THE UNCOMFORTABLE PART OF THAT, AND IT IS THE HONEST READING:
    int4 decode at 1.93 MAC/byte sits only 1.35x below the 2.6 threshold, not
    orders of magnitude below it. So the negative result is NOT robust to a
    batch dimension: external intensity is LINEAR in batch size, so batch 2
    at int4 would cross the line. The reason this is not a hole in the
    finding is that (a) interactive single-user decode is batch 1 by
    definition, and (b) THE MODEL CANNOT CURRENTLY EXPRESS A BATCHED DECODE
    -- it would need the GEMM path plus a KV-cache growth term. Do not quote
    a batched number. Do state that a batched or speculatively-decoded
    workload is a genuinely different point on this plane and is the single
    most likely way this conclusion changes. It is listed in section 6.

  AND THE GAP BETWEEN THE TWO BOUNDARIES IS THE ANSWER TO THE QUESTION:
      differentiated up to  0.00021 G int8 / 0.00066 G int4
      feasible up to        0.32 G int8 / 0.64 G int4   (at 6.4 GB/s, 20 tok/s)
      ratio                 1532x int8 / 967x int4
    So the FEASIBLE-UNDIFFERENTIATED zone is ~1000-1500x wide in model size
    and covers EVERY model anyone would call a language model. The
    DIFFERENTIATED zone tops out around 0.2-0.7 M parameters -- which is not
    a small language model, it is an MLP. The two ML regimes are not two
    sizes of the same workload; they are different workloads, and the
    dividing line is whether the weights live on chip.

========================================================================================================
(3) THE WEIGHT-RESIDENT REGIME — what fits, and is there an ML SKU in it?
========================================================================================================

What fits 192 KB, weights only (leave nothing for activations or a solver):
    int8:    196,608 parameters = 0.000197 G
    int4:    393,216 parameters = 0.000393 G

  The feasible streaming envelope at 6.4 GB/s / 20 tok/s is 0.32 G int8 /
  0.64 G int4 [DER, boundary 1]. What FITS on chip is 0.0002-0.0004 G.
  THOSE TWO NUMBERS DIFFER BY ~1600x, so for LLM decode the resident regime
  and the feasible regime DO NOT OVERLAP AT ALL. There is no scratchpad
  size that turns an LLM into a resident workload -- see the SKU table.

  Resident-weight ML SKU: what would a bigger scratchpad buy and cost?

  READ THE LAST COLUMN. Solver energy is MONOTONE INCREASING in capacity
  (§8: bigger banks, longer bitlines, more pJ/byte on traffic that was
  already resident), so an ML-capacity SKU TAXES EVERY SOLVER ROW -- the
  rows the company is actually sold on. And it does not even buy the ML:
  a 4 MB scratchpad holds 8 M int4 parameters, still ~80x below the 0.64 G
  a 6.4 GB/s stream already delivers. VERDICT: THERE IS NO RESIDENT-WEIGHT
  LLM SKU. The capacity finding does kill it, and it kills it by two
  independent arguments (solver tax AND insufficient reach).

  THE MIDDLE CASE IS DIFFERENT, and it is the one worth having. Real
  networks against 192 KB, alone and co-resident with the flagship solver:
network                               params   int8 KB   int4 KB  fits 192KB?  +QUAD fits?
ANYmal Science-Robotics policy        49,964      50.7      26.3          yes          yes
legged-gym actor                     190,860     190.1      96.9          yes           NO

  So there is NO middle case in the sense the question implied -- no network
  that needs 384 KB-1 MB and repays it. The population is bimodal: MLP
  control policies at 25-200 KB (which fit, or nearly), and everything with
  a convolutional or transformer backbone at 3-6 MB and up (which never
  fits, at any SKU we would build). The 25-200 KB band is EXACTLY the band
  where residency, coherency and one-call fusion apply, and it is also the
  band where the workload is batch-1 GEMV -- the settled bandwidth-bound
  finding, applied to a network instead of a solver. The one thing 256-384
  KB does buy is CO-RESIDENCY with the solver, which is section 4.

========================================================================================================
(4) THE HYBRID LOOP — learned policy -> reference -> MPC solver, one call
========================================================================================================

The claim under test: a learned policy produces a reference or a
constraint, an MPC solver enforces it, both resident on one engine in one
call. Concretely, at 1 kHz on a legged robot:
    policy A: ANYmal Science-Robotics policy
              MLP 48-256-128-32-12, 49,964 params
              [CITE] Hwangbo et al., Sci. Robotics 2019, arXiv:1901.08652
    policy B: legged-gym actor
              MLP 48-512-256-128-12, 190,860 params
              [CITE] Rudin et al., CoRL 2021, arXiv:2109.11978
    solver:   QUAD-MPC, measured footprint 138.8 KiB at fp32 [MEAS]

  (4a) DOES THE COMBINED WORKING SET FIT 192 KB?
combination                               policy KiB  solver KiB  total KiB   of 192   verdict
policy A @ int8                                 50.7       138.8      189.5      99%      FITS

  THE MARGIN IS THE FINDING, AND IT IS THIN.
    policy A @ int8 fits with 2.5 KiB spare of 192 -- 1.3%.
    policy B @ int8 is 328.9 KiB = 171% of capacity: does NOT fit, needs 384 KB.
    policy B @ int4 is 235.7 KiB = 123% of capacity: does NOT fit, needs 256 KB.
  So the hybrid loop is REAL at 192 KB for a Science-Robotics-class policy,
  with ~1% of margin -- which is not a margin, it is a coincidence. For the
  legged-gym default shape (the more widely copied one) it needs 256 KB at
  int4 weights or 384 KB at int8.

  THAT IS A CAPACITY REQUIREMENT AND IT IS THE FIRST ONE IN THE WHOLE
  ANALYSIS THAT IS NOT ABOUT MAKING ONE SOLVER FIT. What it costs, taken
  straight from the section-3 table so the price is attached to the ask:
     256 KB: core 0.832 mm2 (1.06x), solver energy 1.032x, and ZERO latency benefit to any solver row
     384 KB: core 1.015 mm2 (1.29x), solver energy 1.100x, and ZERO latency benefit to any solver row
  Note the arrow: this is the SAME capacity axis §8 struck as a scaling
  axis ("capacity is a cost, 1.29x"). It is still a cost. The difference is
  that a workload is now asking for it, which is the thing §8 said did not
  exist -- so this does not overturn the finding, it supplies the missing
  demand side and prices it.

  Residency is BINARY here and there is no graceful degradation. Policy B at
  int8 in 192 KB re-streams 136.9 KiB EVERY TICK: 21.9 us of a 1000 us period at 1 kHz and
  1.68 uJ against the solve's own 8.90 uJ -- +19% energy for a
  network that is ~4% of the work. The measured 46x residency ratio
  (268 KB first call, then 5.8 KB in / 0.6 KB out per tick [MEAS]) SURVIVES
  co-residency in the fitting cases and is DESTROYED in the others -- there
  is no partial credit.

  Two honest qualifications on that number:
    * The model's overflow term is a uniform 'excess streams every call'
      approximation and does not know WHICH buffer is evicted. Here it
      coincides with what codegen would actually choose -- keep the solver
      data (touched 15-74 times per tick), stream the policy weights
      (touched once) -- so it is the right number and not merely a bound.
      It would NOT be the right number for two workloads with similar reuse.
    * 138.8 KiB is the QUAD-MPC footprint with A = [I;Gamma] exploited. The
      dense-A plan measures 163.8 KiB, which pushes even policy A @ int8 to
      214.5 KiB and OUT of 192 KB. The hybrid loop's fit therefore
      DEPENDS ON A CODEGEN OPTIMISATION, which is a fragile place for a
      product claim to rest. State the 256 KB requirement.

  (4c) END-TO-END TICK: one CM call vs the NPU-plus-CPU split shipped today

  The comparison is charged as generously to the incumbent as it can be:
  THE NPU'S INFERENCE IS FREE. Zero time, zero energy, zero DRAM. That is
  not a modelling convenience, it is the only defensible thing to do -- we
  have no measured NPU data and may not benchmark against vendor claims. If
  we win against a free NPU the result is robust; if we do not, say so.
  The incumbent pays only what is unavoidable and measurable in OUR model:
  one offload launch (T0 = 25.0 us rich host / 2.0 us MCU-class, from the
  decomposed table in argmind_model) plus the CPU's own solve.

  (4d) WHAT ABOUT A PERCEPTION NETWORK RATHER THAN A POLICY MLP? This is the
  version of the hybrid loop the pitch reaches for, and it fails for a
  reason that is not capacity at all:
schedule                            period us    vit us  solve us  stream us   tick us  of period   verdict
ViT+QUAD at ViT's own 30 fps            33333      7598      48.2        882      8529        26%     MEETS
ViT+QUAD in the 1 kHz tick               1000      7598      48.2        882      8529       853%    MISSES
    READ WHICH COLUMN IS BIG. At 30 fps the pair is comfortable (26% of the
    period). In a 1 kHz tick it misses by 8.5x, and it misses on COMPUTE:
    7598 us of array-bound GEMM against 882 us of streaming and 48 us of
    solve. So co-residency is not even the binding problem here -- a ViT
    frame does not fit a 1 ms budget on a 144-MAC array at ANY capacity or
    bandwidth, and buying the 5.7 MB that would make it resident (6.3x core
    area, 2.2x solver energy, section 3) would not help by a single
    microsecond. The binding resource is the one thing §8 says does not
    scale usefully (MAC array, 1.00x), which is why this is a scope
    boundary and not a provisioning request.
    THE HYBRID LOOP ONLY CLOSES WHEN THE NETWORK RUNS AT THE CONTROL RATE,
    AND THAT FORCES THE NETWORK TO BE AN MLP. Perception at 30 Hz next to
    control at 1 kHz is the CONSOLIDATION-ACROSS-LOOPS question §8 already
    settled: capacity-bound rather than throughput-bound, needing
    descriptor-granularity preemption. Different product question, and this
    is a second workload pointing at the same requirement.

  WHAT THIS ACTUALLY SAYS, and it is less than the pitch wants:
    * The network is 1.1-4.0% of the tick's compute and a similar share of
      its energy. THE HYBRID LOOP'S ADVANTAGE IS THE SOLVER'S ADVANTAGE.
      Fusing the policy in does not create a new claim; it removes a REASON
      TO BUY A SECOND ENGINE, and it removes one offload launch per tick.
    * Both sides MEET the 1 kHz deadline. Same story as every solver row:
      we are more efficient, not enabling. Do not pitch feasibility.
    * The offload launch we delete is 25 us on a rich host and 2 us on an
      MCU-class one. At 1 kHz that is 2.5% / 0.2% of the period -- material
      only above ~10 kHz, which is consistent with the settled finding that
      the invocation argument needs a deadline above ~100 kHz to decide
      anything. DO NOT SELL THE HYBRID LOOP ON LAUNCH OVERHEAD.
    * The claim that DOES survive is architectural and capacity-shaped:
      ONE ENGINE, ONE ADDRESS SPACE, ONE STATICALLY ALLOCATED WORKING SET,
      and therefore ONE deterministic worst-case tick covering perception
      and control together. A robot today cannot state a joint worst case
      across an NPU and a CPU sharing DRAM. That is a determinism claim,
      which is already one of the three that survive against a vector CPU.

========================================================================================================
(5) THE BASELINE PROBLEM — why no ML perf/W number here is a claim
========================================================================================================

Every perf/W figure above divides a modelled CM energy by a modelled CPU
energy. On solver rows that is the right comparison: an MPC solver runs on
the application core today, and the in-order A55 baseline is deliberately
the least flattering choice available.

ON ML ROWS IT IS THE WRONG COMPARISON AND WE KNOW IT. Nobody runs edge CNN
inference on a Cortex-A when the SoC has an NPU. VIT-TINY's 28.2x is a
comparison against a baseline no engineer would choose. (Note in passing:
the figure sometimes quoted for that row is 30.4x. The model has said
28.22x since the 192 KB capacity correction and
results_scaling_study.txt records 28.22x -- use the recorded value.)
The honest adversary is the NPU, and we cannot run that comparison:
  * we have no MEASURED NPU silicon energy at a stated node and precision;
  * our evidence standard forbids comparing a modelled figure against a
    vendor marketing claim, which is all that is published; and
  * an inference-optimised int8 macro (or a CIM macro) is designed for
    exactly the operand-reuse pattern a CNN has, which is the one pattern
    where our bandwidth-first provisioning is NOT the right shape.

  So the conclusion is stronger than 'scope the ML claim narrowly':

    THE ML INFERENCE-EFFICIENCY CLAIM IS UNSUPPORTED, NOT MERELY NARROW.
    It is unsupported in the specific sense that the only baseline we can
    model is one no customer would deploy. Removing it costs nothing,
    because it was never going to survive a customer architect's whiteboard.

  WHAT IS LEFT, AND IT IS NOT NOTHING. Three ML-adjacent claims that do not
  require an inference-efficiency comparison at all:
    1. ARITHMETIC RETARGETABILITY. NPU IP is int8-weights-only (Ethos-U85)
       or ~1% of int8 throughput at FP32 (Ceva). That is a capability
       statement about the rival, measurable from its own datasheet, and it
       is why an NPU cannot run the solver half of a hybrid loop at all.
    2. CO-RESIDENCY AND ONE DETERMINISTIC TICK, quantified in section 4:
       the pair fits 192 KB for a Science-Robotics-class policy and needs
       256-384 KB for the legged-gym default. A joint worst-case tick is
       something an NPU-plus-CPU split cannot state.
    3. MACIF. The answer to 'an inference macro beats you on TOPS/W' is
       'yes, and it plugs in here' -- which requires int4 to be a DECLARED
       format, not an assumed one.

  MACIF CONSEQUENCE OF int4, and it is the mirror image of fp16-vs-bf16:
    * A macro that silently substitutes int8 for int4 returns the RIGHT
      answer and loses 2x of bandwidth. That is a performance regression,
      not a wrong answer -- the OPPOSITE failure mode from bf16-for-fp16,
      and it must still be refused, because a codegen plan that assumed 2x
      the operand bandwidth will miss its deadline.
    * A macro that substitutes int4 for a declared int8 kernel is a WRONG
      ANSWER and must be refused in the same class as a missing fp64 path.
    * Substitution is therefore asymmetric in CONSEQUENCE and symmetric in
      POLICY: refuse both directions, report which kind of failure was
      avoided.

========================================================================================================
(6) WHAT WOULD FALSIFY ANY OF THIS
========================================================================================================

  * A MEASURED NPU energy figure at a stated node and precision. It is the
    single missing input; everything in section 5 turns on its absence. An
    eval board and a power rail settles it -- the same instruction as
    falsifier F4.
  * A BATCH DIMENSION, and this is the one most likely to bite. External
    intensity is LINEAR in batch size and the differentiation threshold is
    ~2.6 MAC/byte, so int4 decode at 1.93 needs only batch 2 to cross it.
    Speculative decoding and multi-request serving both produce an effective
    batch >1. The model CANNOT currently express a batched decode (it would
    need the GEMM path plus a KV-growth term), so no batched number is
    quotable -- but the negative result above is explicitly a BATCH-1 DECODE
    result and must never be restated as an LLM result.
  * An L0 operand register file, already flagged as the top model extension:
    it raises on-chip intensity and would make the GEMM/ViT regime cheaper
    still. It does NOT touch the LLM regime, because the binding resource
    there is off chip.
  * A measured accuracy result at int4 on a control-relevant network. This
    module models bytes and cycles only; if int4 costs a policy its
    behaviour, every int4 row above is a datapath capability with no
    workload attached.
