====================================================================================================
fp64 DATAPATH — COSTING THE LARGEST UN-COSTED ITEM IN THE CM-100 BUDGET
16nm-class, MODELLED ESTIMATES +/-2x (fp64 gate count carries a further
2.1x band). NOT QUOTABLE EXTERNALLY.
====================================================================================================

HEADLINE: 8 merged multi-format FMA units (1x fp64 or 2x fp32 each).
  Binding constraint on ARM-MPC becomes the fp64 FMA CLUSTER, not
  scratchpad bandwidth -- the one documented exception to bandwidth-first,
  and it holds because ARM-MPC is 79% matrix-MATRIX (block Riccati).

====================================================================================================
Q1 — GATE-COUNT BASIS AND THE THREE OPTIONS
====================================================================================================
Parametric IEEE-754 FMA gate model (sram_cost.fma_gates_ieee):
  gates = 4.5*n^2 + 240*n + 1200, n = significand bits;  0.26 um2/NAND2 at 16nm
  format      n    kgates   mm2/unit  x bf16 cell
  bf16        8      3.41    0.00106        1.00x
  fp16       11      4.38    0.00137        1.29x
  fp32       24      9.55    0.00298        2.80x
  fp64       53     26.56    0.00829        7.79x

  CALIBRATION: fp32 -> 9.6 kgates, fp64 -> 26.6 kgates (ratio 2.8x).
  Cross-check at the low end: the model gives 3.41 kgates at n=8 against the
  independently-guessed 3.0 kgates for the bf16/fp32-acc array cell -- 14% apart, weak but real corroboration.
  PESSIMISTIC EDGE [C4]: a measured 28nm dual-precision FMA is 56.2 kgates, 2.1x
  the parametric value. Every fp64 area number below is given at both.

----------------------------------------------------------------------------------------------------
(a) MULTI-PASS DECOMPOSITION onto the existing bf16 multipliers
----------------------------------------------------------------------------------------------------
  This is the option that looks free and is not. THE PASS COUNT IS THE
  WHOLE STORY, and it is a published number, not a guess:
    FP16 inputs, FP32 accumulate, FP64-accurate DGEMM: 25-196 GEMM passes [C1]
    FP8(E4M3) inputs:                                  121 GEMM passes [C1]
    bfloat16 inputs (8 mantissa bits, extrapolated):    49-361 passes [EST from C1]
    bfloat16 for fp32-EQUIVALENT accuracy only:         6-9 passes

  THAT ASYMMETRY IS THE FINDING. Multi-pass on bf16 reaches fp32 accuracy
  in 6-9 passes and fp64 accuracy in 49-361. fp32 is precisely the
  precision interior point cannot use [C5]. So the cheap version of this
  option does not deliver the capability, and the version that delivers
  the capability is not cheap. Costing it anyway, on the CM-100 array,
  ARM-MPC at 30 IP iterations (worst case), deadline 4000 us:

   passes  fp64 MAC/cyc   array us   GEMV us  issue us   TOTAL us        uJ  vs native verdict             
        9          16.0      365.4      47.5     243.0      655.9     36.57       0.8x MEETS 50% budget (fp32-acc only)
       25           5.8     1015.0      79.2     675.0     1769.2     86.20       1.9x MEETS 50% budget    
       49           2.9     1989.4     110.9    1323.0     3423.3    156.01       3.4x deadline only       
      121           1.2     4912.6     174.3    3267.0     8353.9    356.21       7.7x MISSES DEADLINE     
      196           0.7     7957.6     221.9    5292.0    13471.5    559.37      12.0x MISSES DEADLINE     
      361           0.4    14656.6     301.1    9747.0    24704.7    998.92      21.5x MISSES DEADLINE     
  NATIVE (8 FMAs)           8.0                                     822.1     46.47       1.0x MEETS 50% budget    

  THE SEQUENCER COST, checked explicitly because that is where the hidden
  expense usually lives. The result is NOT what was expected:
    * 180 descriptors per IP iteration (N=30 stages x ~6 block ops) [EST]
    * consistency check: that makes the average block op 514 MACs,
      i.e. only 5.6 array cycles on 144 MACs at 63% utilisation
    * against 8 sequencer cycles to issue one descriptor [EST]

    So the issue-to-compute ratio is:
      seq cyc/descriptor  issue:array ratio  consequence
                       2              0.35x  array-bound
                       4              0.71x  array-bound
                       8              1.42x  SEQUENCER-ISSUE-BOUND
                      16              2.84x  SEQUENCER-ISSUE-BOUND

    TWO THINGS FOLLOW, and only one of them is about multi-pass:
    1. The ratio is P-INDEPENDENT. Both terms scale with the pass count,
       so multi-pass does not make the sequencer tax relatively worse.
       The expected hidden expense is NOT there. Multi-pass is killed by
       the pass count alone.
    2. The ratio ALSO seemed to flag a separate, pre-existing problem: at
       nb=21 an HPIPM block op looked like only a handful of array cycles,
       so if descriptor issue cost >4 cycles ARM-MPC would be
       SEQUENCER-ISSUE-BOUND rather than array-bound 'at any precision'.
       That was LOGGED here as an open item and has since been CLOSED --
       AS A UNIT ERROR IN THIS FILE. See perf_model/sequencer.py and
       PHASE0_FINDINGS.md 0.2. The table above divides by the 144-MAC bf16
       ARRAY rate, but ARM-MPC is fp64 and fp64 runs on the 8-unit FMA
       CLUSTER -- which is the decision THIS FILE makes two sections
       earlier. Corrected, and with the descriptor count fixed at its
       structural value (540/IP iteration, 3x the 180 assumed here), the
       figure is 30 datapath cycles per descriptor against a crossover at
       34 setup cycles: ARRAY-BOUND, with 8.6x margin at 4 cycles/desc.
       'At any precision' is FALSE -- exposure scales with arithmetic
       RATE, so fp64 is the SAFEST case and fp32/bf16 the most exposed.
       The table below is therefore correct ONLY for the multi-pass option
       it prices, where the work really is on the bf16 array.
       NEW CONSEQUENCE FOR Q3: the fp32 + iterative-refinement option puts
       the O(n^3) factorisation on the array in fp32, where the crossover
       is 10 setup cycles -- so refinement is SEQUENCER-ISSUE-BOUND with
       anything but a hardware descriptor generator. Q3 does not charge
       it for that. Native fp64 wins on a third axis.

  AND THE ACCUMULATOR, which is the part of option (a) that has real area:
    error-free slice accumulation needs an exact 128-bit fixed-point
    accumulator per participating output element [C2], vs the 32-bit fp32
    accumulator already in the cell. Widening the array's accumulators:
        16 accumulators: +0.0044 mm2
        64 accumulators: +0.0176 mm2
       144 accumulators: +0.0395 mm2
    So option (a) costs 0.0395 mm2 of added accumulator against the
    +0.0670 mm2 fp64 increment of the recommended option (d).

  WHY (a) IS REJECTED — stated honestly, because the deadline argument is
  NOT as clean as it first looked:
    * The AREA SAVING IS 0.0275 mm2, ~4% of the core. That is the whole prize.
    * The pass count is 49-361 [EST extrapolated from C1] -- a 7x band
      whose optimistic edge meets the raw 4000 us deadline and whose
      pessimistic edge misses it by 6x. Taking a 7x-uncertainty
      dependency on the ONE hard-real-time correctness path to save 4%
      of the core is a bad trade at any pass count in that band.
    * ENERGY, which is the axis we actually sell: 3.4x to 21.5x worse
      than native (156-999 uJ vs 46 uJ), because P passes multiply BOTH the
      MAC energy and the sliced-operand fetch traffic. This alone settles
      it: an energy-differentiated part cannot use a 4-30x energy penalty
      on a beachhead workload to save 4% of its area.
    * MACIF: error-free limb splitting plus an exact 128-bit accumulator
      is a contract no analog CIM macro can honour (see Q5). Option (a)
      would push a strong exactness requirement INTO the swappable macro.
    REJECTED — on energy and on interface risk, not on the deadline.

  Where multi-pass IS right: a THROUGHPUT fp64 part (HPC DGEMM), where
  49-361 passes still beat having no fp64 silicon at all and there is no
  deadline. We are building a DEADLINE part with ~4 FMAs of fp64 demand.
  Where it is ALSO right, and worth keeping in codegen: reaching fp32
  accuracy from bf16 multipliers in 6-9 passes, which is how the fp32 rows
  already work (2-pass split, exact in the fp32 accumulator).

(c) NATIVE fp64 WIDENED THROUGH THE WHOLE ARRAY
----------------------------------------------------------------------------------------------------
    64 merged fp64-capable cells: 0.689 mm2 central / 1.448 mm2 pessimistic
   144 merged fp64-capable cells: 1.551 mm2 central / 3.258 mm2 pessimistic
   256 merged fp64-capable cells: 2.758 mm2 central / 5.792 mm2 pessimistic
  vs 144 bf16 cells today: 0.135 mm2
  Net +1.417 mm2 to the compute block -- roughly 12x option (b) --
  which would take the CM-100 core from 0.565 to ~2.19 mm2, a 3.9x part, to
  serve ONE benchmark whose demand is 4-8 FMAs. Also pointless on its own
  terms: at 144 fp64 FMAs ARM-MPC lands at 202 us, 10x inside the
  50%-period budget, and its fp64 GEMV is bandwidth-capped at 16 MAC/cycle
  regardless -- so most of the array is unfeedable even on the one
  benchmark that wants fp64 at all. REJECTED.

----------------------------------------------------------------------------------------------------
(d) RECOMMENDED — MERGE THE fp64 CLUSTER WITH THE fp32 VECTOR UNIT
----------------------------------------------------------------------------------------------------
  A separate fp64 cluster is idle on 6 of the 7 benchmarks. But the CM-100
  already carries 16 fp32 vector lanes, and 8 merged multi-format FMAs
  ARE 16 fp32 lanes (1x fp64 or 2x fp32 per unit) [C3]. So build one
  block. The fp64 capability then costs only the WIDENING, not a unit:
    honest fp32-only 16-lane vector unit   0.0577 mm2
    merged 8x(fp64 | 2x fp32) + transcend.  0.1247 mm2
    => fp64 INCREMENT                      +0.0670 mm2 central
       pessimistic edge                    +0.1950 mm2

  STRUCTURAL HAZARD to write down: the block cannot be the vector unit and
  the fp64 GEMM engine in the same cycle. On ARM-MPC the vector term is
  30 us against 582 us of fp64 GEMM, so serialising costs
  ~4% of the budget. On the fp32 rows the block is 100% vector unit.
  Acceptable. But it makes the vector unit and the fp64 unit ONE
  scheduling resource, which the sequencer model and codegen must know.

Q2 — HOW MUCH fp64 THROUGHPUT DOES THE BENCHMARK SET ACTUALLY REQUIRE?

  Everything else is fp32 (ADMM-MPC, EKF) or int8 (ML). The EKF floor is
  fp32 and there is no fp16/bf16 filter path -- but no fp64 requirement
  either, so fp64 demand comes from interior point alone.

  ARM-MPC at 15 IP iterations — typical (p95 design point)
    fp64 GEMM (block Riccati)    1,574,370 MACs (79% of fp64 work)
    fp64 GEMV (substitutions)      414,540 MACs
    total                        1,988,910 MACs

    minimum for the 50%-of-period budget : 4 FMAs
    minimum for the raw 4000 us deadline : 2 FMAs
    minimum at TYPICAL 15 iterations     : 2 FMAs   <-- why typical cannot size
    optimistic utilisation proxy (dim=79) : 4 FMAs

  ANSWER: 4 FMAs is the feasibility FLOOR; 8 is the recommendation, at
  2.43x margin on the 50%-period budget and 4.87x on the
  raw deadline. 2 FMAs misses the budget, 1 misses the deadline outright.
  8 is chosen over 4 because it is FREE: 8 merged units is exactly the
  16 fp32 vector lanes the part already needs. Above 8, fp64 GEMV becomes
  bandwidth-bound at 16 MAC/cycle and the extra units buy 64 us on a 2000 us
  budget -- not worth 0.07 mm2. This is a genuine local optimum, not a
  round number.

  ADVERSARIAL CHECK on the softest assumption in this sizing. fp64_util
  softens the 2-D quantisation penalty by a square root, on the argument
  that a LINEAR cluster only quantises its innermost loop. That is worth
  1.26x. Re-run with the FULL 2-D penalty charged instead:
   FMAs   harsh us  budget margin   deadline
      2     3516.3          0.57x      1.14x
      4     1909.8          1.05x      2.09x
      8      971.2          2.06x      4.12x
     16      637.2          3.14x      6.28x
  The recommendation is UNCHANGED (8 FMAs, 2.25x instead of 2.70x) and so
  is the floor (4 FMAs, 1.14x instead of 1.38x -- thin either way). So the
  sizing does not depend on the softening. What it DOES depend on is
  iters_worst=30, which is [EST] (2x the design point), not measured:
   iters_worst  floor (>=1x budget)   8-FMA budget margin
            30                   4 FMAs                 2.43x
            45                   6 FMAs                 1.65x
            60                   8 FMAs                 1.25x
  At a 60-iteration tail the 8-FMA recommendation drops to 1.39x margin --
  still feasible, but no longer comfortable. MEASURING ARM-MPC'S ACTUAL
  IP ITERATION TAIL IS THE SINGLE HIGHEST-VALUE INPUT TO THIS DECISION,
  ahead of the gate count and ahead of the energy constant.

  SO THE HONEST HEADLINE IS: a very small fp64 cluster suffices. The
  previous 0.125-rate-factor model was over-providing fp64 by 2.25x
  (18 vs 8 MAC/cycle) at zero area, so its ARM-MPC latency was optimistic
  by the same factor on the fp64 GEMM term.

Q3 — DOES fp32 + ITERATIVE REFINEMENT BEAT NATIVE fp64?
====================================================================================================
  FIRST, THE ARGUMENT THAT SETTLES IT BEFORE ANY MODELLING [C5]:
  fixed-precision refinement converges only while cond(A)*eps < 1. The
  interior-point endgame has cond(KKT) ~ 1e12 and eps_fp32 ~ 6e-8, so the
  product is ~6e4 >> 1. fp32-working-precision refinement DOES NOT
  CONVERGE there. Mixed-precision refinement works, but it requires the
  RESIDUAL in higher precision than fp32 -- i.e. fp64 hardware.
  => Refinement RELOCATES the fp64 requirement from the O(n^3)
     factorisation to the O(n^2) residual. It never removes it. There is
     no version of this that lets us ship without an fp64 datapath.

  SECOND, THE ECONOMICS AT OUR BLOCK SIZES. The asymptotic case for
  refinement is 'residual O(n^2) is cheap against factorisation O(n^3)'.
  Ratio = 3k/nb. At nb=21 (7-DoF arm, n_x+n_u):
    k=1: residual work is  14.3% of the factorisation
    k=2: residual work is  28.6% of the factorisation
    k=3: residual work is  42.9% of the factorisation
    k=5: residual work is  71.4% of the factorisation
  Refinement is only 'cheap' (<10%) when nb > 30k, i.e. nb > 90 at k=3.
  EMBEDDED MPC LIVES AT nb = 10-30. The asymptotic argument for iterative
  refinement does not transfer to this problem class. That is a real
  finding and it is the opposite of the HPC intuition.

  THIRD, THE MODELLED COMPARISON on the SAME silicon (144-MAC bf16/fp32
  array + 8 fp64 FMAs + 128 B/cycle), ARM-MPC at 30 IP iterations:

  strategy                              lat us       uJ   spad MB  fp64 frac  determinism
  S1 all-fp64 KKT solve                  822.1    46.47     10.44       100%  fixed op count
  S2 fp32 factor + fp64 IR, k=1          301.5    31.17     11.57         8%  fixed k
  S2 fp32 factor + fp64 IR, k=2          403.5    46.06     17.92        13%  fixed k
  S2 fp32 factor + fp64 IR, k=3          505.5    60.94     24.27        16%  fixed k
  S2 fp32 factor + fp64 IR, k=5          709.6    90.72     36.97        20%  fixed k

  READ THIS TABLE ADVERSARIALLY, because it does NOT simply favour us.
  Refinement is FASTER at every k (1.2x-2.7x). On ENERGY there is a
  CROSSOVER at k = 3: below it refinement wins on energy too, above it
  native fp64 wins. So the honest statement is a crossover, not a verdict:

    k <= 2   fp32 + refinement is better on latency AND energy
    k >= 3   native fp64 is better on energy, still slower

  Mechanism: refinement moves 2.3x the scratchpad bytes at k=3 -- it
  re-reads the KKT matrix in fp64 for every residual, k times per IP
  iteration, to avoid reading it in fp64 once for the factorisation. That
  is why the O(n^2)-is-cheap intuition fails: at nb=21 the residual is not
  cheap, and it is the fp64-traffic term.

  WHICH SIDE OF THE CROSSOVER ARE WE ON? k >= 3, and not by our choice.
  At cond ~1e12 with fp32 working precision the refinement iteration does
  not contract at all [C5] -- k is not 1 or 2, it is UNBOUNDED unless the
  residual and the correction solve are themselves done in fp64, in which
  case the fp64 traffic is worse still. The energy crossover therefore
  lands on the wrong side of the numerics, and the numerics are not
  negotiable.

  FOURTH, DETERMINISM — the decisive point for a hard-deadline part.
  k is DATA-DEPENDENT. Two ways to handle it, both bad:
    (i)  adaptive k: worst-case latency is unbounded. Non-starter.
    (ii) fixed k with a correctness check and an all-fp64 fallback:
         deterministic, but the certifiable worst case is the SUM.
    S1 alone                          822.1 us
    S2 (k=3) alone                    505.5 us
    S2 then fallback to S1           1327.6 us  <-- the number a safety
                                              argument must use
    ... which is 1.6x S1 alone. A scheme whose WORST case is worse than
    the thing it replaces cannot be the baseline for a hard-deadline part,
    however good its average case is.

  VERDICT FOR A HARD-DEADLINE PART: native fp64. Grounds, in order of
  strength: (1) refinement does not remove the fp64 requirement at all,
  it relocates it; (2) its worst-case-with-fallback latency exceeds
  all-fp64; (3) past the k the numerics force, it is worse on energy;
  (4) ARM-MPC already has 4.9x deadline margin all-fp64, so the latency
  refinement buys is margin we do not need. Keep S2 as an OPTIONAL codegen
  mode for soft-deadline / throughput use; do not make it the baseline.
  CAVEAT: this rests on a citation [C5], not on our own measurement.
  Measuring the actual refinement count in acados/HPIPM is item 2 below.

  DOES THE ANSWER DIFFER FOR THE SOLVER-ONLY SKU (64 MACs, 64 B/cycle)?
    S1 all-fp64         822.1 us    54.59 uJ
    S2 k=3              758.8 us    76.18 uJ
    NO -- and for a structural reason worth stating: the fp64 cluster is
    NOT part of the MAC array, so it does not scale down with the SKU.
    S1 latency is EXACTLY identical on both parts (822 vs 822 us) because
    both are fp64-cluster-limited, and at 64 B/cycle the fp64 GEMV
    bandwidth ceiling (8 MAC/cyc) exactly equals the cluster width. Energy is
    1.17x higher only because the smaller tile fetches more GEMM operand
    bytes per MAC (2.00 vs 1.33 B/MAC). What DOES change materially is the area FRACTION:
      CM-100         fp64 increment 0.0670 mm2 = 8.5% of 0.786 mm2 core
      solver-only    fp64 increment 0.0670 mm2 = 10.2% of 0.654 mm2 core
    So fp64 is proportionally MORE expensive on the small part -- and the
    small part is the MPC-only SKU that most needs it. There is no SKU
    from which fp64 can be removed while keeping interior-point MPC.
    Dropping to 4 FMAs there gives only 1.24x budget margin: too thin. Keep 8.

  perf/W — IS THE 2.20 pJ/fp64-MAC ESTIMATE LOAD-BEARING? YES.

  Derivation check on the constant first. Horowitz (ISSCC 2014, 45nm)
  gives fp32 mult 3.7 pJ + fp32 add 0.9 pJ. Multiplier energy scales as
  the significand squared: (53/24)^2 = 4.9x, the adder
  roughly linearly. Weighting the multiply at 70% of FMA energy gives
  fp64/fp32 = 4.1x, so from E_MAC_PJ[fp32]=0.6 pJ the
  n^2-consistent fp64 figure is 2.45 pJ against the 2.2 pJ in the model.
  The constant is ~13% optimistic on its own internal logic. Within noise,
  but the direction is worth knowing.

   fp64 pJ/MAC    ARM uJ   perf/W vs best CPU  vs 5x kill
          2.20     25.23                17.2x        PASS
          3.30     29.60                14.6x        PASS
          4.40     33.98                12.8x        PASS
          6.60     42.73                10.1x        PASS

  fp64 MAC energy is 35% of ARM-MPC's 25.2 uJ/call at the typical
  iteration count -- the single largest term. SENSITIVITY: the kill
  criterion survives a 3x error in the constant, so the go/no-go does not
  depend on it; the QUOTED RATIO does, by about 2x across the band.
  MEASUREMENT THAT SETTLES IT: gate-level power on one merged fp64 FMA at
  800 MHz. CVFPU is open source; this is a day of work, not a study.

  SME2 part without it has no fp64 matrix path at all. Check the target's
  ID registers on an eval board before claiming anything either way.

  ARM-MPC's REPORTED perf/W THEREFORE MOVES 14.1x -> 19.8x. That is a
  flattering change and it must be decomposed, not banked:
    * CM side got WORSE: fp64 throughput 18 -> 8 MAC/cycle raised latency
      178 -> 213 us (typical) and energy 19.6 -> 22.5 uJ via static power.
    * CPU side got worse FASTER: charging fp64 at half the fp32 rate took
      the A55 baseline 276 -> 445 uJ. That is 1.6x, against our 1.15x.
    * NET: the whole increase comes from the CPU-side bug fix, none of it
      from anything we designed. Both changes are corrections of errors
      that pointed in opposite directions and happened to partly cancel.
    * SANITY CHECK the fix is not overdone: the A55 baseline still MEETS
      ARM-MPC's raw 4000 us deadline (2880 us). We are not claiming the
      CPU cannot do this -- only that it costs 20x the energy. Consistent
      with CLAUDE.md's standing instruction.

  ALSO NOTE what did NOT change: with fp64 throughput decoupled from the
  MAC array, ARM-MPC is now FLAT across the tile-size sweep. The old
  0.125 factor made a bigger array look like it bought fp64 speed. It
  never did, and now the model says so.

====================================================================================================
Q5 — THE MACIF CONSEQUENCE
====================================================================================================
  fp64 CANNOT be a swappable-macro property hidden behind MACIF. The
  interface must carry PRECISION AS A DECLARED CONTRACT. Four reasons,
  in descending order of how expensive it is to get wrong:

  1. IT IS AN ALGORITHM REQUIREMENT, NOT A PERFORMANCE KNOB. Interior
     point at cond ~1e12 either has fp64 or produces a wrong answer [C5].
     A boundary that lets a macro silently substitute lower precision
     converts a swap decision into a correctness failure in the field.
     Precision must be QUERYABLE and the runtime must REFUSE an fp64
     kernel on a macro that does not declare fp64 -- a hard error at
     codegen time, not a degraded result at run time.

  2. THE fp64 UNIT IS ON THE OTHER SIDE OF THE BOUNDARY FROM THE ARRAY.
     The whole point of MACIF is that a digital-CIM or analog macro can
     replace the MAC array. Neither can do fp64: analog CIM has no path
     to 53-bit significands, and digital CIM at fp64 is not a product.
     So the fp64 FMA cluster must sit OUTSIDE the MACIF boundary, in the
     fixed part of the CM, alongside the vector unit it is merged with.
     That is the architectural consequence of this whole analysis: the
     boundary runs between the bf16/int8 array (swappable) and the
     fp32/fp64 FMA cluster (not swappable). Drawing it anywhere else
     makes the interior-point path un-portable.

  3. MULTI-PASS EMULATION WOULD HAVE LEAKED ACROSS THE BOUNDARY ANYWAY.
     Option (a) needs error-free integer/limb semantics and an exact
     128-bit accumulator INSIDE the macro [C2]. That is a much stronger
     contract than 'multiply and accumulate approximately', and an analog
     macro cannot honour it at all. Choosing option (b)/(d) keeps MACIF's
     contract weak enough to be honourable by a CIM macro -- which is the
     entire value of having the boundary.

  4. IT IS A FEATURE BIT, NOT A SCALING PARAMETER. Q3 showed the fp64
     cluster is the same 8 units on the 144-MAC part and the 64-MAC part.
     Interface fields that scale with the array (MAC count, tile shape,
     operand width) must therefore NOT be the same fields that describe
     fp64. Concretely, MACIF v0 should declare, per format:
       supported {int8, bf16, fp16, fp32, fp64}
       macs_per_cycle[format]        (absolute, not a rate factor)
       accumulator_width[format]     (exactness contract)
       rounding mode + subnormal behaviour  (IEEE conformance claim)
     The 0.125 rate factor this run deleted is precisely the shape of
     interface that would have been wrong: a scalar multiplier on a bf16
     capability, implying fp64 falls out of the array for free.
